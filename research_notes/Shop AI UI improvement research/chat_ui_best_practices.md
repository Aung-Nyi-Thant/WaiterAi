# Chat UI Best Practices for Restaurant/Food-Ordering Assistants

## What are current best practices for perceived responsiveness in AI chat UIs (streaming vs. single-shot reveal), and is streaming worth the effort for a local-LLM restaurant bot?

### Takeaway
Token-by-token streaming is the industry-standard technique for perceived latency because it converts "waiting" into "reading," and is considered the single most effective perceived-latency technique in LLM chat UX; a typing indicator alone is a real but much weaker mitigation. For a local-LLM (Ollama) restaurant bot with multi-second latency, streaming is worth adding if engineering time allows, but a well-designed "thinking" state (not just generic dots) with capped, punchy replies can close most of the gap cheaply.

### Cited Findings
- Streaming text, where tokens appear progressively rather than all at once, is described as the single most effective approach to perceived latency in LLM latency guidance — it converts a "waiting" experience into a "reading" experience — because the first word can appear in 200–600ms and the user starts reading immediately even though total time is unchanged — [TianPan.co / Latency Perception Gap](https://tianpan.co/blog/2026/04/20/latency-perception-gap-ai-interfaces)
- A peer-reviewed study found instant responses averaged a satisfaction score of 5.67, long responses with no indicator dropped to 4.40, and adding a typing indicator significantly mitigated (but did not eliminate) the negative effect of long latency — [arXiv: Mitigating Response Delays in Free-Form Conversations with LLM-powered Intelligent Virtual Agents](https://arxiv.org/pdf/2507.22352)
- A three-dot typing indicator is "slightly better than nothing" but "nowhere near the engagement level of true streaming" because it tells the user the system is working but not what it's doing, how far along it is, or what the result will look like — [Nowah: Streaming UX](https://nowah.xyz/blog/streaming-ux-real-time-ai-responses)
- Streaming LLM responses is cited as reducing perceived latency by roughly 40–60% (one source), and streaming API responses by 60–80% versus waiting for the complete response (another source) — [TokenMix AI Streaming Guide](https://tokenmix.ai/blog/ai-api-streaming-guide); [AI/TLDR: Designing for LLM Latency](https://ai-tldr.dev/learn/building-ai-apps/ai-ux-patterns/designing-for-llm-latency/) — note: the two percentage ranges come from different secondary-source blog posts, not a single primary benchmark, so treat the exact numbers as directional rather than precise.
- Three latency metrics matter for chat UX: TTFT (time-to-first-token, "the number a user judges you on"), TPOT (time per output token — how fast text visibly scrolls), and total latency ≈ TTFT + (output_tokens × TPOT); a 400ms TTFT with a 6-second total can still "feel responsive" — [DEV Community: TTFT vs Total Latency](https://dev.to/gabrielanhaia/ttft-vs-total-latency-instrumenting-what-users-actually-feel-5h0f)
- Trimming input tokens (prompt size) has been observed to shave a small amount off total latency (roughly 1–5% per 50% reduction), i.e. prompt-trimming helps but is a minor latency lever compared to streaming — [DEV Community: TTFT vs Total Latency](https://dev.to/gabrielanhaia/ttft-vs-total-latency-instrumenting-what-users-actually-feel-5h0f)
- NN/g's own chatbot design guidance explicitly discusses scroll-position behavior "especially with streaming responses" (recommending the view not aggressively auto-scroll to the very end while text is still arriving), implying streaming is treated as an expected, mainstream pattern for AI chat UIs today — [NN/g: 10 Guidelines for Designing Your Site's AI Chatbots](https://www.nngroup.com/articles/ai-chatbots-design-guidelines/)

### Inferences
- For Shop AI specifically: since replies are generated by a local Ollama model (multi-second, possibly variable latency) with template-based safety overrides for allergens/prices, true token streaming requires the backend to support incremental generation (Ollama's API does support streaming responses) and the frontend to render partial text — a moderate but not huge engineering lift given the stack is already Next.js/React.
- Given the safety-override pattern (templated replies for allergens/prices), those specific replies could be delivered instantly/whole (no need to stream a static template), while only free-form LLM-generated replies would stream — a hybrid approach that limits engineering scope to the paths that actually have multi-second latency.
- If full token streaming is judged too costly for the current sprint, the highest-leverage low-effort improvement is replacing the generic "typing dots" with a more informative progress/status state (e.g., "Thinking about the menu…" or showing the dish name once identified before the full sentence is ready) plus keeping replies short (the app already caps reply length per recent commit history), since shorter output directly reduces total latency (fewer tokens to generate) independent of streaming.

### Gaps
- No source directly benchmarks streaming vs. non-streaming UX specifically for a *local* (on-device/on-prem) LLM restaurant/food-ordering assistant, nor for Ollama specifically — findings are generalized from broader LLM chat UX literature, not restaurant-specific or Ollama-specific studies.
- No primary-source (e.g., OpenAI's own published latency guide) was directly fetched; the "OpenAI latency guide" claims came from secondary summaries referencing it, not the primary document itself, so attribute that framing to secondary sources with caution.

## What are best practices for structured/rich replies in chat (dish cards, images, prices, "add to order" actions inline) — spacing, density, and how leading apps handle mixed text+card content?

### Takeaway
Leading guidance and food-delivery bot patterns converge on: always show images with product recommendations, keep the reply text short and let a card/carousel do the visual work, make the primary action (e.g. "Add") a clearly tappable button rather than requiring more chat turns, and use progressive disclosure (expand/collapse) for extra detail instead of spawning more chat messages.

### Cited Findings
- NN/g's chatbot guidance explicitly recommends "Include images, not just product names or descriptions" for product recommendations and instructional guidance — [NN/g: 10 Guidelines for Designing Your Site's AI Chatbots](https://www.nngroup.com/articles/ai-chatbots-design-guidelines/)
- The same NN/g guidance recommends using accordions to expand/collapse details inline rather than generating new chat messages that lengthen the conversation (progressive disclosure) — [NN/g: 10 Guidelines for Designing Your Site's AI Chatbots](https://www.nngroup.com/articles/ai-chatbots-design-guidelines/)
- NN/g also recommends allowing users to resize/maximize the chat window specifically when it needs to display maps, product carousels, or other detailed rich content — [NN/g: 10 Guidelines for Designing Your Site's AI Chatbots](https://www.nngroup.com/articles/ai-chatbots-design-guidelines/)
- NN/g recommends presenting suggested/follow-up actions "as clickable buttons, rather than text" to reduce friction and typing burden — [NN/g: 10 Guidelines for Designing Your Site's AI Chatbots](https://www.nngroup.com/articles/ai-chatbots-design-guidelines/)
- Food delivery chatbots typically use carousel elements so users can scroll a food menu, with quick-reply buttons appearing after item selection to ask about size/options, and product carousels display scrollable cards with images, prices, and buy buttons — the visual presence of the product image itself increases click-through versus text-only listings — [Lazarev.agency: Chatbot UI examples](https://www.lazarev.agency/articles/chatbot-ui-examples); [storeagent.ai: Chatbot UI Examples](https://storeagent.ai/chatbot-ui-examples/)
- A described best-practice pattern for food-delivery-style bots: tailored recommendation prompts ("Surprise Me," "Top picks for you"), a clean visual layout with high-quality food images to simplify decision-making, and clearly displayed contextual details (e.g., pickup time/distance) — [InspoAI: AI Food Delivery UI Generator](https://www.inspoai.io/solutions/ai-food-delivery-ui-generator)
- One synthesis explicitly frames the "hybrid layout": rich media cards with images, specs, and price shown in a single view, with inline recommendations for complementary items — i.e., don't force users to scroll through many separate small cards when one denser card plus a short list of add-ons works better — [Eleken/Lazarev-style chatbot UI roundups](https://www.lazarev.agency/articles/chatbot-ui-examples)

### Inferences
- Shop AI's current pattern (inline dish card under the assistant's text reply with photo, name, price, "Add" button) already matches the core NN/g recommendation (image + name + price, one-tap action) — the main gap opportunities are (a) whether multiple dish suggestions in one reply are shown as a scrollable carousel vs. stacked cards (stacked full-width cards for 1–2 items, carousel only if 3+, is a reasonable density rule), and (b) whether tapping "Add" requires confirmation/quantity selection inline (a small quick-reply-style stepper) rather than a full navigation away from chat.
- Because this is a phone-width, QR-opened responsive web session (not a native app with a maximizable window), the NN/g "resizable window" recommendation doesn't map directly — the equivalent for Shop AI would be making sure dish cards render at a size that doesn't force horizontal scrolling or excessive vertical scrolling on a small phone viewport, and that the full-screen chat sheet itself already gives maximum vertical space (which it does).

### Gaps
- No source specifically documents optimal card sizing/spacing metrics (e.g., exact px/rem card height, gap size) for chat-embedded product cards on mobile web — this is more a general mobile-card-density design question than a distinctly "chat AI" one, and wasn't directly answered by sources found.
- No direct case study of ChatGPT's or Claude's own apps rendering commerce-style product cards inline was found in this pass (their public design guidelines don't focus on commerce cards); findings here lean more heavily on food-delivery bot roundups and NN/g's general e-commerce chatbot guidance than on general-purpose LLM chat apps.

## What are best practices for suggested-reply chips/quick actions in chat (when to show, how many, persistence vs. first-message-only)?

### Takeaway
Chips should be short (2–4 words / under ~20 characters), few in number (to avoid decision paralysis), always dismissible/never block the composer, and ideally refresh dynamically as the conversation progresses rather than appearing only once — NN/g documents "conversation starters" (first-turn, capability-teaching chips) as a distinct pattern from "follow-up suggestions" (recurring, generated after each reply), and treats both as legitimate, separate uses of prompt controls.

### Cited Findings
- Suggestion chips should be dismissible and should never block the message composer, preserving user control — [Setproduct Blog: Designing AI chat interfaces](https://www.setproduct.com/blog/ai-chat-interface-ui-design)
- Recommended chip copy: short phrases, ideally under 20 characters, aiming for 2–4 words per button so users can scan and understand instantly — [Uxcel: How to Design UI Chips](https://uxcel.com/lessons/anatomy-694); [BuiltABot: Quick Reply Generator](https://www.builtabot.com/tools/quick-reply-generator)
- Tapping a chip should immediately send it as a message, and the UI should then refresh with a new set of suggestions (i.e., chips are not necessarily one-time/first-turn-only — they can recur every turn) — [Sendbird: 15 Chatbot UI examples](https://sendbird.com/blog/chatbot-ui)
- A commonly cited (unsourced/marketing-style) statistic claims users are "40% more likely to continue conversations when quick replies are available" — flagged here as a claim from an aggregator blog without a traceable primary study, so treat as a directional claim, not a hard statistic — [storeagent.ai: Chatbot UI Examples](https://storeagent.ai/chatbot-ui-examples/)
- Explicit anti-pattern: avoid non-dismissible suggestions that always funnel users toward predetermined paths — if the user already knows what they want, unwanted suggestions become friction; and too many choices cause decision paralysis, so only the most common paths should be surfaced — [storeagent.ai: Chatbot UI Examples](https://storeagent.ai/chatbot-ui-examples/)
- NN/g distinguishes multiple "prompt control" patterns: (1) **Conversation starters** — task examples shown up front that "aim to teach users what the bot can do" (i.e., a first-turn, capability-teaching use, matching Shop AI's current first-message-only chips); (2) **Prompt libraries** — a larger up-front set of ~10 example prompts users can pick or edit (e.g., ChatGLM's "Inspiration Center"); (3) **Follow-up suggestions** — suggestions generated *after* a reply (e.g., Perplexity surfaces three related follow-up questions after every answer, explicitly to "save the user from manually typing" and to "provide inspiration for other questions"); (4) **Quick modification controls** — buttons for common transformations of the last reply (e.g., Google Gemini's "Shorter / Longer / More casual") — [NN/g: Prompt Controls in GenAI Chatbots](https://www.nngroup.com/articles/prompt-controls-genai/)
- NN/g's general prompt-control guidance (not chip-count-specific) stresses using standard icons/labels or tooltips, grouping related controls to avoid overwhelming the user, and following existing UI conventions — [NN/g: Prompt Controls in GenAI Chatbots](https://www.nngroup.com/articles/prompt-controls-genai/)

### Inferences
- Shop AI's current behavior (chips only on the first message) matches NN/g's "conversation starter" pattern, which is a legitimate, well-precedented pattern on its own — but NN/g's article shows that top-tier products (Perplexity, Gemini) additionally use a *second*, distinct chip pattern after every subsequent reply ("follow-up suggestions"), which Shop AI currently lacks. Adding a small (2–3), dynamically-generated set of follow-up chips after each assistant reply (e.g., "See vegetarian options," "Show spicy dishes," "Any drink pairing?") would align with the more complete, higher-end pattern and reduce typing on a phone — the highest-value, most concretely actionable chip improvement identified in this research.
- Given the source-flagged anti-pattern (chips must stay dismissible and not block the composer), Shop AI should verify that once a user starts typing, or once several turns have passed without tapping a chip, the composer remains fully usable and chips don't visually compete with or overlay the text input.

### Gaps
- No source gives a precise numeric ceiling on chip count backed by a controlled study (e.g., "exactly 3 is optimal") — the "few, not many, to avoid decision paralysis" guidance is qualitative across all sources, not quantitatively validated in what was found.
- No source specifically addresses persistence *across* multiple conversation sessions (e.g., should chips reappear if a diner leaves and reopens the chat sheet later in the same visit) — only within-conversation turn-by-turn guidance was found.

## What are best practices for user feedback capture (thumbs up/down) — placement, follow-up on thumbs-down, and what happens with the feedback?

### Takeaway
Thumbs up/down should be a zero-friction, always-visible control on every assistant message (first layer), with a thumbs-down click expanding into a short categorized reason picker (second layer) and an optional free-text field for the minority who want to elaborate (third layer); after submission the controls should visually confirm receipt (e.g., disable/replace with a "Thanks, feedback recorded" message) and feedback should be stored in a structured backend table rather than just logged informally.

### Cited Findings
- Thumbs up/down icons should be attached to every response, always visible, and require zero extra clicks to capture the most basic signal — minimal friction is what drives a higher volume of feedback compared to lengthy surveys — [The Training Boss: Thumbs Up & Down for LLM Responses](https://thetrainingboss.com/thumbs-up-down-for-llm-responses/)
- The recommended architecture is tiered: Layer 1 = thumbs up/down on every response (zero extra clicks); Layer 2 = on thumbs-down, expand a short form with predefined categories such as "Inaccurate," "Not relevant," "Incomplete," or "Harmful" (predefined categories are faster to act on than open text); Layer 3 = an optional "Tell us more" free-text field for the minority of users willing to elaborate, which provides the highest-value qualitative signal even though most users won't use it — [The Training Boss: Thumbs Up & Down for LLM Responses](https://thetrainingboss.com/thumbs-up-down-for-llm-responses/)
- Implementation guidance: allow feedback only once per response/run, and once a user clicks thumbs up/down, replace the control with a confirmation state such as "Thanks, your feedback has been recorded" rather than leaving it clickable/ambiguous — [The Training Boss: Thumbs Up & Down for LLM Responses](https://thetrainingboss.com/thumbs-up-down-for-llm-responses/)
- Recommended backend flow: the frontend sends a feedback payload (which message, thumbs up/down, optional category/comment) to the backend, which validates and stores it in a dedicated feedback table — i.e., feedback should be structured/queryable data, not just an event fired into generic analytics — [The Training Boss: Thumbs Up & Down for LLM Responses](https://thetrainingboss.com/thumbs-up-down-for-llm-responses/)

### Inferences
- Shop AI already has thumbs up/down per assistant message, which matches Layer 1 of the recommended architecture. The clearest, concrete gap is the missing Layer 2: a thumbs-down tap currently (per the task description) does not appear to prompt a reason. Adding a lightweight, restaurant-relevant category picker on thumbs-down (e.g., "Wrong info," "Didn't understand my question," "Rude/off-tone," "Missed allergen concern") would be low-effort UI (a small popover/sheet) and turn a single bit of signal into an actionable one, directly useful for prompt/model tuning.
- Because this is a QR-code, largely anonymous diner session (no persistent account), the value of Layer 3 (free-text "tell us more") is lower than in a logged-in product — most anonymous diners are unlikely to type more, so Layer 2's predefined categories are likely the highest-value addition relative to effort, while Layer 3 could be optional/skippable.

### Gaps
- No source specifically discusses what to do with restaurant-chatbot feedback operationally (e.g., does it feed into a manager dashboard, retrain prompts, alert staff for a bad experience in real time) — general LLM-app guidance was the closest available source, not restaurant-specific feedback-ops guidance.
- No source addressed whether thumbs-down should ever trigger an *immediate* in-chat response (e.g., bot auto-apologizing or auto-escalating to "Call staff") versus purely silent backend logging — this remains an open design decision not covered by available sources.

## What are best practices for error/fallback messaging when the assistant can't answer (ambiguous, out-of-scope, safety-relevant like allergens) — tone, escalation, UI treatment?

### Takeaway
Fallback messages should avoid generic, dead-end apologies and instead be honest about the limitation while always offering a concrete next step (rephrase, or a persistent, one-tap path to a human); for safety-relevant topics specifically (allergens, in Shop AI's case), the assistant should never guarantee safety, should explicitly disclose it may not be fully accurate/complete, and should route to human/staff verification as the final authority — with escalation ideally triggered automatically after repeated fallbacks, not just by user request.

### Cited Findings
- When a chatbot cannot handle an unexpected question, the key design guidance is to avoid generic apologies that offer no path forward, and instead provide alternatives or a handoff to a human agent — [uxcontent.com: Designing chatbots: how to design fallback logic](https://uxcontent.com/designing-chatbots-fallbacks/)
- Recommended fallback message framework: anticipate common failure points and provide responses that acknowledge confusion honestly (e.g., "I'm not sure I understood — could you rephrase?"), and always offer a way to start over or reach a human — the fallback message should be honest about the limitation without undermining the user's confidence in the system overall — [uxcontent.com: Designing chatbots: how to design fallback logic](https://uxcontent.com/designing-chatbots-fallbacks/)
- Escalation is described as a "handoff from chatbot to human agent," distinguishing a *planned* escalation (a designed step in the flow) from a *fallback* escalation (triggered specifically because the bot failed to resolve intent) — [Kommunicate: What is Fallback Message?](https://www.kommunicate.io/what-is/fallback-message/)
- Recommended escalation *triggers* (not just availability) include: an explicit user request for a human, a repeated-fallback counter (e.g., fallback_count >= 2 within a conversation), and low-confidence responses on high-value/high-risk intents (the source's examples are refunds/billing — the direct analogy for Shop AI is allergens/pricing) — [Beefed.ai: Chatbot Fallback & Escalation Best Practices](https://beefed.ai/en/chatbot-fallback-escalation)
- When the bot fails to understand or complete a request, best practice is to be transparent that the system is having trouble and to provide a clear resolution path; a simple, broadly-cited way to achieve this is a persistent "talk to an agent" (or equivalent) option always visible in the UI — [Beefed.ai: Chatbot Fallback & Escalation Best Practices](https://beefed.ai/en/chatbot-fallback-escalation)
- Human-handoff UX guidance frames good escalation as preserving conversation context across the transition (the human should not make the user repeat themselves) and states that trust is won or lost specifically at the escalation moment, not during ordinary bot answers — poor implementations create "loops" and a "buried escape hatch," and a human who arrives asking "so, how can I help you today?" as if nothing happened is cited as the canonical failure mode — [Asks.app: AI-to-human handoff](https://asks.app/blog/ai-human-handoff); [AI UX Playground: Human Handoff pattern](https://www.aiuxplayground.com/pattern/human-handoff/)
- A "visible lifeboat" pattern — a persistent, always-present "talk to a human" affordance (the source cites Amazon's persistent chat-with-agent button as an example) — is recommended so users are never forced to hunt for the escape hatch — [Asks.app: AI-to-human handoff](https://asks.app/blog/ai-human-handoff)
- Restaurant-specific allergen safety guidance: chatbots should never guarantee an allergen-free dish, should keep allergens, complaints, and unconfirmed bookings "behind clear human guardrails," should carry a clear disclaimer that the AI's information may not be 100% accurate or cover all allergen notices, and should treat human staff verification as mandatory for any allergy/dietary/health-related uncertainty — clear disclaimers are explicitly framed as building trust, not eroding it — [brand.menumiz.com: AI Restaurant Bots That Work](https://brand.menumiz.com/2026/01/31/why-most-ai-restaurant-bots-fail-and-what-actually-works/); [Hostie.ai: Voice AI That Handles Allergy & Dietary Questions Safely](https://hostie.ai/resources/voice-ai-allergy-dietary-questions-menu-aware-bots-2025)

### Inferences
- Shop AI already has template-based safety overrides for allergens/prices and an always-visible "Call staff" bell, which structurally matches the "visible lifeboat" + "planned escalation for high-risk intents" best practice at the system level. The main opportunity is at the *messaging* layer: ensure the allergen-related templated reply itself contains an explicit, human-readable disclaimer (not just a redirect) — e.g., "I can share general dish info, but I can't guarantee allergen safety — please confirm with staff" rather than a bare deflection — and that this reply visually/behaviorally nudges toward the "Call staff" button (e.g., the bell button could be highlighted or the templated reply could include an inline "Call staff" action) rather than relying on the diner to notice the always-present bell separately.
- For ordinary ambiguous/out-of-scope (non-safety) questions, the concrete, low-effort improvement is ensuring the fallback copy always pairs the apology with either a rephrase prompt or a suggested chip pointing at something answerable, rather than a bare "I don't understand" — this is directly actionable in prompt/template copy with no new UI components required.
- A repeated-fallback counter (auto-suggesting "Call staff" after e.g. 2 consecutive low-confidence/fallback replies in a row) is a concrete, implementable escalation trigger beyond the current "always-visible bell" (which relies entirely on the diner's own initiative to escalate).

### Gaps
- No source gives restaurant-QR-chatbot-specific data on how often diners actually notice/use a persistent human-escalation button versus abandoning the chat — general SaaS/customer-support handoff literature was the closest available, not physical-restaurant/QR-context-specific.
- No source addressed tone calibration specifically for a warm/hospitality context (as opposed to neutral SaaS support tone) — none of the fallback-copy sources found were restaurant/hospitality-specific in their example wording.

## What are accessibility best practices specific to chat interfaces (screen reader announcements, focus management, keyboard navigation of a full-screen chat sheet/modal)?

### Takeaway
New assistant messages should be announced via a polite ARIA live region (`role="log"`, `aria-live="polite"`, without `aria-atomic`, so only the newly appended message is read rather than the whole transcript), while opening the full-screen chat sheet should follow standard modal-dialog focus-management rules (`aria-modal="true"`, focus moved into the dialog on open, a trapped/cyclic tab order, and focus returned to the trigger element on close); this combination is also the direct implementation path for WCAG 2.1/2.2 Success Criterion 4.1.3 (Status Messages).

### Cited Findings
- Use `role="log"` with `aria-live="polite"` for real-time chat so screen reader users are updated on new messages without disrupting their current focus; the `log` role represents a live region where new information is added in meaningful order and old information may disappear, with chat logs/message histories given as the canonical example — [Ionic: Aria Live Regions Accessibility Guide](https://ionic.io/docs/accessibility/aria-live)
- For chat messages, use `role="log"` *without* setting `aria-atomic`, so that only the newly appended message is announced rather than the entire transcript being re-read each time; when a new message arrives, append it to the list so only the new item triggers an announcement — [Ionic: Aria Live Regions Accessibility Guide](https://ionic.io/docs/accessibility/aria-live)
- The live region container should be present and empty in the DOM before content is added (best practice: if injecting the live region dynamically, wait at least ~2 seconds for assistive-tech APIs to register it before pushing text into it), and should carry a clear `aria-label` such as `aria-label="Chat messages"` — [The A11Y Collective: Complete Guide to ARIA Live Regions](https://www.a11y-collective.com/blog/aria-live/)
- General live-region hygiene: use `polite` for non-critical/ordinary updates and `assertive` only for urgent updates; keep announced text short and clear; avoid overloading a page with many live regions (recommended: at most one polite region and one assertive region, both present from page load rather than injected ad hoc); test across multiple screen readers (NVDA, JAWS, VoiceOver) since behavior can differ — [The A11Y Collective: Complete Guide to ARIA Live Regions](https://www.a11y-collective.com/blog/aria-live/)
- WCAG 4.1.3 (Status Messages, Level AA) requires that status messages — including "waiting state," "progress of a process," and existence-of-errors messages — be programmatically determinable without receiving focus, i.e. implementable primarily via ARIA live regions with roles like `role="status"` or `role="alert"`; the "someone is typing" state is explicitly cited as an example status message in the chat context — [WCAG.com: 4.1.3 Status Messages](https://www.wcag.com/developers/4-1-3-status-messages/); [W3C: Understanding SC 4.1.3](https://www.w3.org/WAI/WCAG21/Understanding/status-messages.html)
- Standard modal-dialog focus rules (W3C WAI-ARIA Authoring Practices Dialog/Modal pattern): when a modal opens, focus must move into the dialog immediately, stay trapped inside it (Tab/Shift+Tab cycle only within the dialog, wrapping from last→first and first→last), and return to the element that triggered the dialog when it closes; initial focus placement depends on dialog content, defaulting to the first focusable element unless another element is more appropriate — [W3C WAI-ARIA APG: Dialog (Modal) Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/); [Deque: WAI-ARIA Modal Alert Dialogs](https://www.deque.com/blog/aria-modal-alert-dialogs-a11y-support-series-part-2/)
- Setting `aria-modal="true"` on the dialog tells assistive technology that the user cannot interact with or access other page content until the modal is closed — [MDN: aria-modal attribute](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-modal)

### Inferences
- Shop AI's "full-screen chat sheet" should be marked up as a proper modal dialog (`role="dialog"` or `"alertdialog"`, `aria-modal="true"`, labelled title) with focus moved to it on open (e.g., to the message input or a close button) and returned to the "Call staff"/chat-launcher trigger on close — if this isn't already implemented, it is a concrete, scoped accessibility fix independent of any visual redesign.
- The message transcript area should be a single persistent `role="log"` + `aria-live="polite"` region (present in the DOM from when the sheet mounts, not injected later) so that each new assistant message — and, notably, the "typing dots" loading state itself — is announced as a status update; this directly also satisfies WCAG 4.1.3 for the "AI is thinking" state, which a purely visual typing-dots animation does not satisfy on its own for screen-reader users.
- Because dish cards are rich, interactive content embedded inside a live region, they should be appended as complete, already-rendered elements (image alt text, dish name, price, and an accessibly-labelled "Add" button, e.g. `aria-label="Add Kung Pao Chicken to order, $12.50"`) so that the live-region announcement is meaningful and the interactive "Add" control is immediately reachable by keyboard/tab order right after the message that introduced it — sources didn't address commerce-card content specifically, but this follows directly from combining the `role="log"` guidance with standard accessible-name best practice for buttons.

### Gaps
- No source specifically discussed keyboard-navigation order or accessible-name conventions for *interactive rich cards inside a live chat log* (e.g., a dish card with an "Add" button embedded mid-transcript) — the inference above is a reasonable synthesis of the live-region and general button-labeling guidance found, not a directly cited best practice.
- No source addressed accessibility specifically for a *mobile-web* full-screen sheet opened via QR code (e.g., interactions between browser chrome, on-screen keyboard, and focus trapping on iOS Safari/Android Chrome, which are known to have quirks with `aria-modal` and virtual keyboards) — the general WAI-ARIA modal guidance is device-agnostic and doesn't cover these mobile-web-specific edge cases.
