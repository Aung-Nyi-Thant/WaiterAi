# Frontend Design-System & CSS Architecture Best Practices (for a hand-rolled CSS Next.js/React app)

## What are the tradeoffs of adopting Tailwind CSS or a component library (shadcn/ui, Radix) versus continuing with hand-rolled CSS, for a small team maintaining a multi-surface app? What migration effort/risk is typical?

### Takeaway
For a small team, hand-rolled CSS is viable but requires self-imposed discipline that a framework would otherwise enforce automatically; Tailwind buys speed and consistency at the cost of HTML/JSX readability and a learning-curve tax, while shadcn/ui (copy-in components, not an npm dependency) is a comparatively low-risk, incremental way to add accessible primitives without a full rewrite — a realistic full migration of an already-sized component set takes on the order of one engineer-week and should be done component-by-component, not as a "big bang."

### Cited Findings
- "Tailwind trades HTML readability for CSS consistency, while vanilla CSS trades setup speed for long-term flexibility. Neither tradeoff is universally right." — [Measured: Understanding the trade-offs of using Tailwind CSS](https://measured.co/blog/tailwind-trade-offs)
- "Two developers on the same project can produce wildly different CSS architectures if nobody enforces conventions. Tailwind externalizes discipline into the framework, while vanilla CSS requires you to build the discipline yourself." — [Measured: Understanding the trade-offs of using Tailwind CSS](https://measured.co/blog/tailwind-trade-offs)
- "Tailwind is fast to learn but you will spend your first weeks looking things up, while hand-written CSS is slow to learn but the knowledge is transferable to every tool that sits on top of CSS." — [Solid Web: Tailwind CSS vs. Vanilla CSS in 2026](https://solid-web.com/tailwind-vs-css/)
- "For startups & MVPs, Tailwind wins (speed over purity); for large teams, a hybrid works best: Tailwind for utilities, custom CSS for complex components." — [Solid Web: Tailwind CSS vs. Vanilla CSS in 2026](https://solid-web.com/tailwind-vs-css/)
- On shadcn/ui specifically: components are copied into the codebase rather than installed as an opaque dependency, so the team "owns the code" and can adapt it directly to existing tokens — [Fordel Studios: Design Systems from Scratch: A Small Team Playbook](https://www.fordelstudios.com/research/design-systems-from-scratch-small-teams)
- A concrete migration-effort data point (Radix→Base UI inside a shadcn project, ~50 component files, dozens of `asChild` call sites, ~100 Tailwind utilities keyed to `data-state`) was estimated at "one focused engineering week of mechanical work," recommended as a gradual, component-by-component replacement rather than a global one — [ShadcnDeck: Radix vs Base UI](https://www.shadcndeck.com/blog/radix-vs-base-ui) / [21st.dev: Radix, Base UI and shadcn](https://21st.dev/blog/radix-base-ui-shadcn)
- shadcn/ui's official stance: Radix is not deprecated even though Base UI became the new default in July 2026; "if you have no specific Radix pain, stay on Radix... if you're hit by long-standing Radix bugs (combobox, focus, form integration), migrating to Base UI offers real fixes" — [shadcn/ui changelog: July 2026 — Base UI as the Default](https://ui.shadcn.com/docs/changelog/2026-07-base-ui-default)
- CSS Modules vs. Tailwind maintainability verdict: "CSS Modules win for maintainability in projects requiring custom, semantic styles... Tailwind wins for rapid UI development, design systems, and teams that want co-located styles"; Tailwind's own maintainability risk is "class string length," where a complex element accumulates dozens of utility classes making JSX harder to read — [Generalist Programmer: CSS Modules vs Tailwind CSS](https://generalistprogrammer.com/comparisons/css-modules-vs-tailwind)

### Inferences
- Given Shop AI's small size (~120-line globals.css, a fixed set of utility classes, no build-tooling investment yet), a full framework swap is disproportionate risk for the near term; the lower-risk path is to keep the existing hand-rolled utility-class vocabulary (`.btn`, `.chip`, `.pill`, etc.) but formalize it as a lightweight token system (see design-token question below), which captures most of Tailwind's consistency benefit without a rewrite.
- shadcn/ui (or Radix primitives alone) is worth considering specifically for the interactive, accessibility-sensitive components the report likely already has hand-rolled versions of — `.modal`, `.toast`, `.switch` — since headless primitives solve focus-trapping, keyboard nav, and ARIA wiring that hand-rolled CSS-only components tend to under-implement. This could be adopted incrementally per-component without touching the surrounding hand-rolled CSS/tokens.
- A full Tailwind migration's risk is chiefly about JSX churn (every `className` string touched) and a learning-curve dip for a "small student/team project," which is a real cost when there's no dedicated frontend owner; the shadcn "copy-in, no external dependency" model is a smaller commitment because it can be trialed on one component at a time and rolled back by deleting a file.

### Gaps
- No source directly compares migration risk/effort specifically for a Next.js *App Router* + React 19 project of Shop AI's exact size (roughly a few dozen components); the one-week estimate found is for a Radix→Base UI swap inside an already-Tailwind/shadcn codebase, not a hand-rolled-CSS→Tailwind migration, so it should be treated as a rough proxy, not a direct estimate.
- No hard data found on defect/regression rates typically introduced during such migrations for small teams specifically (vs. enterprise case studies).

## What are current best practices (2025-2026) for glassmorphism: accessibility/contrast, performance cost of backdrop-filter on mobile, and when it's appropriate vs. overused?

### Takeaway
Glassmorphism has a structural accessibility problem — translucent panels sit over unpredictable backgrounds, so a component's contrast ratio is not a fixed property of the component but of whatever happens to be behind it, making WCAG 2.2 AA compliance (4.5:1 body text, 3:1 large text) impossible to guarantee in advance; the 2025-2026 consensus is to use glass sparingly (accents, modals, players, notifications), always add a semi-opaque scrim/fill behind text, cap `backdrop-filter` blur usage per screen for mobile GPU cost, and honor `prefers-reduced-transparency`.

### Cited Findings
- WCAG 2.2 requires a minimum contrast ratio of 4.5:1 for normal text and 3:1 for large text (18pt/14pt bold+) — [Understanding Success Criterion 1.4.3: Contrast (Minimum), W3C WAI](https://www.w3.org/WAI/WCAG21/Understanding/contrast-minimum.html); [figr.design: Glassmorphism guide](https://figr.design/blog/glassmorphism-0e8b1)
- "Glassmorphism is a WCAG 2.2 violation in most of its implementations due to a structural incompatibility between what glassmorphism requires to look like glassmorphism, and what accessible text requires to be readable." — [Codexical: Glassmorphism Is the Best-Looking Design Trend That Fails Accessibility](https://www.codexical.com/posts/2026-04-24-glassmorphism-accessibility)
- Concrete measured example: the *same* translucent component achieved 5.2:1 contrast over a dark wallpaper but only 1.8:1 over a light one — i.e., the background, not the component, determines pass/fail, which makes advance verification impossible — [Codexical, citing Axess Lab testing](https://www.codexical.com/posts/2026-04-24-glassmorphism-accessibility)
- Common "fixes" that are really removals of the glass effect: a dark scrim overlay (leaves "glass edges and a dark box where the text is"), raising panel opacity to 85-90% (panel then "looks like a slightly blurry solid color"), or a fully solid fallback fill — [Codexical](https://www.codexical.com/posts/2026-04-24-glassmorphism-accessibility)
- Recommended test method: check contrast at the worst-case point under the text (not the average), and test the same component over at least ~5 different backgrounds/wallpapers with a contrast analyzer — [Codexical](https://www.codexical.com/posts/2026-04-24-glassmorphism-accessibility); WCAG guidance concurs that gradient/image backgrounds must be tested at their lowest-contrast point since WCAG itself gives no formula for translucent/gradient backgrounds — [WebAIM: Contrast and Color Accessibility](https://webaim.org/articles/contrast/); [ACHECKS: Gradients accessible colour contrasts](https://www.achecks.org/gradients-accessible-colour-contrasts-with-gradient-backgrounds/)
- Other accessibility risks beyond contrast: visual clutter from partially-visible background content disrupting focus; animated blur/parallax effects that "can make people with vestibular conditions feel lightheaded or queasy"; glass styling obscuring which elements are interactive for users who scan quickly or use screen magnifiers — [Axess Lab: Glassmorphism Meets Accessibility](https://axesslab.com/glassmorphism-meets-accessibility-can-frosted-glass-be-inclusive/)
- Recommended mitigations: maintain a semi-opaque fill/overlay behind text (never compromise contrast for the aesthetic), respect `prefers-reduced-transparency` and `prefers-reduced-motion`, add subtle borders to reinforce which regions are distinct/interactive, and test with screen readers, varied visual acuity simulations, high-contrast OS modes, and low-power devices — [Axess Lab](https://axesslab.com/glassmorphism-meets-accessibility-can-frosted-glass-be-inclusive/)
- `backdrop-filter` performance: it is GPU-accelerated compositing, but web.dev explicitly warns "backdrop-filter may harm performance. Test it before deploying." — [web.dev: Create OS-style backgrounds with backdrop-filter](https://web.dev/articles/backdrop-filter)
- Mobile-specific guidance: mobile devices "typically handl[e] 3-5 simultaneous blur effects well," but heavy/large-area or many-element use of `backdrop-filter` is GPU-intensive and should be used sparingly, and can lead to janky scrolling and reduced battery life on low-powered devices — [multiple secondary sources synthesizing this point](https://blog.openreplay.com/creating-blurred-backgrounds-css-backdrop-filter/); performance-overuse warning also echoed independently — [Pravin Kumar: Should You Use Glassmorphism on Your Website in 2026?](https://www.pravinkumar.co/blog/should-you-use-glassmorphism-website-2026)
- Fallback strategy for unsupported browsers/perf-constrained cases: use `@supports not (backdrop-filter: blur(1px))` to substitute a fully opaque background, and for performance reasons prefer a plain solid/image fallback over attempting to polyfill the blur — [web.dev](https://web.dev/articles/backdrop-filter); [figr.design](https://figr.design/blog/glassmorphism-0e8b1)
- `prefers-reduced-transparency`: a CSS media feature (Chrome/Edge 118+, Firefox behind a flag as of the sources found) that detects a user's OS-level "reduce transparency" setting (available in Windows, macOS, iOS, Android accessibility settings); recommended pattern is additive — build a solid, accessible baseline and only add transparency inside `@media (prefers-reduced-transparency: no-preference)`, rather than trying to strip it out inside a `reduce` block — [Chrome for Developers: CSS prefers-reduced-transparency](https://developer.chrome.com/blog/css-prefers-reduced-transparency); [MDN: prefers-reduced-transparency](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-reduced-transparency)
- On appropriate use: "Glassmorphism is a spice, not a meal — a little makes a design feel current and considered, but too much makes it slow, unreadable, and dated the moment the trend turns." Cited good-fit surfaces: modals/notification overlays, media players, onboarding screens, finance/weather dashboards; the trend was "turbocharged" industry-wide by Apple's 2025 "Liquid Glass" design language at the same time a backlash against overuse was already building — [Pravin Kumar: Should You Use Glassmorphism on Your Website in 2026?](https://www.pravinkumar.co/blog/should-you-use-glassmorphism-website-2026)

### Inferences
- Shop AI's `.aurora-d`/`.gd` and `.aurora-l`/`.gl` themes are applied as whole-screen backgrounds on diner/staff and owner/auth surfaces respectively — i.e., large-area, persistent glass rather than a small accent — which is closer to the "overused" end of the spectrum the sources warn about, both for contrast risk (many different text elements sit over the same blurred background across a whole screen) and for mobile performance (diner is explicitly a 390px phone surface, staff/waiter also phone-based — exactly the device class flagged for backdrop-filter GPU cost).
- Because the glass surfaces are whole-screen rather than small floating panels, the "test over 5 wallpapers" method is less relevant (the background is fixed and known), but the core fix set still applies directly: add solid/semi-opaque backing behind body text and small UI text specifically (the utility classes like `.chip`, `.pill`, `.meter` likely need per-class contrast auditing against the actual `.gd`/`.gl` background colors, not just eyeballing), and add `@media (prefers-reduced-transparency: reduce)` overrides that raise opacity toward solid for both themes.
- Given diner/waiter are phone surfaces, auditing/reducing simultaneous `backdrop-filter` regions per screen (e.g., not stacking a blurred modal on top of an already-blurred `.aurora-d` background) is a concrete, low-effort mobile-performance fix.

### Gaps
- No source gave a specific FPS/jank benchmark number for `backdrop-filter` on a specific low-end Android/iOS chip; guidance found is qualitative ("3-5 simultaneous effects," "test before deploying") rather than a hard performance budget.
- No source addressed whether stacking a full-screen glass background (as Shop AI does) *underneath* additional glass components (modals, toasts) compounds cost differently than isolated floating glass panels — this is an inference, not a cited fact.

## What are best practices for implementing true user-togglable dark/light mode in a CSS-custom-properties system — `prefers-color-scheme`, `data-theme`, persistence, avoiding flash of wrong theme in Next.js?

### Takeaway
The standard, low-risk pattern is: store the user's explicit choice (not just system preference) in a cookie (readable server-side) or `localStorage`, apply it via a `data-theme` attribute (or class) on `<html>`, and set that attribute *before* first paint via either a synchronous inline `<script>` in `<head>` or, better in the App Router, by reading a cookie in the root Server Component layout and rendering the attribute server-side — `next-themes` is the de facto library that packages this pattern and additionally distinguishes the user's stated preference ("system") from the resolved theme actually applied.

### Cited Findings
- The flash of wrong theme (FOWT) happens because "the browser parses HTML and renders CSS using default values before JavaScript runs to apply the correct `data-theme` attribute," and in the App Router "the server doesn't know the user's theme preference—that's stored in localStorage or a cookie on the client—so the server renders with the default theme and JavaScript must later correct it." — [dev.to: How to Prevent the Flash of Wrong Theme](https://dev.to/137foundry/how-to-prevent-the-flash-of-wrong-theme-when-implementing-dark-mode-2pg1); [dev.to: Building a Dark Mode System in Next.js App Router — Without Layout Flash](https://dev.to/aon_infotech_3a1b6ff525fc/building-a-dark-mode-system-in-nextjs-app-router-without-layout-flash-5gf9)
- `next-themes`' `ThemeProvider` "automatically injects a script into `next/head` to update the `html` element with the correct attributes before the rest of your page loads," using `localStorage` (default key `'theme'`) for persistence and a `data-theme` (default) or class attribute on `<html>` for application — [GitHub: pacocoursey/next-themes](https://github.com/pacocoursey/next-themes)
- `next-themes` models two separate values: `theme` (the user's stated preference, which can literally be `"system"`) and `resolvedTheme` (what "system" actually resolves to at runtime) — this lets a toggle UI show "System/Light/Dark" while styling logic always has a concrete resolved value — [GitHub: pacocoursey/next-themes](https://github.com/pacocoursey/next-themes)
- Cookies are recommended over `localStorage` specifically because they're sent with the HTTP request, so a Server Component can read the cookie and render `<html data-theme="dark">` (or via class) directly in the server-rendered HTML — "ensuring that the correct theme is applied the moment the browser loads the HTML, providing a flicker-free user experience" and "eliminating the flash entirely for server-rendered pages" — [dev.to: Building a Dark Mode System in Next.js App Router](https://dev.to/aon_infotech_3a1b6ff525fc/building-a-dark-mode-system-in-nextjs-app-router-without-layout-flash-5gf9); also argued directly in [Medium: Don't use LocalStorage for Dark Mode in Next.js: Here's a Better Way](https://medium.com/@kjinengineer/dont-use-localstorage-for-dark-mode-in-next-js-here-s-a-better-way-f6d4c98c3c07)
- Whichever storage is used, "you need to apply the theme before React hydrates" — i.e., a synchronous inline script (not a `useEffect`, which runs after hydration and still flashes) is required if not using the cookie/Server-Component approach — [dev.to: How to Prevent the Flash of Wrong Theme](https://dev.to/137foundry/how-to-prevent-the-flash-of-wrong-theme-when-implementing-dark-mode-2pg1)
- Design-token integration pattern: define separate light/dark token sets as CSS variables, scope them to a `[data-theme='dark']` (etc.) selector, and have the theme provider only need to toggle that one attribute for every component referencing tokens (e.g. `var(--color-primary)`) to re-theme automatically — [Handoffpro: design tokens react](https://www.handoffpro.dev/blog/design-tokens-react); [Designdev: Building a design token system with CSS custom properties](https://www.designdev.io/posts/building-a-design-token-system-with-css-custom-properties-and-tailwind-v4)

### Inferences
- Shop AI's current setup — two *hardcoded* glass themes assigned per surface (dark glass for diner/staff, light glass for owner/auth) rather than a togglable light/dark preference — is a different axis than "dark/light mode" as the sources describe it: it's a *role-based skin* (which surface you're on) not a *brightness preference* (what the viewer wants to see). Implementing "true" user-togglable dark/light mode without breaking the deliberate per-surface design most likely means introducing a second, independent attribute (e.g. `data-theme="dark|light"` for brightness alongside something like `data-surface="diner|owner|staff|chef"` for the glass skin), so a user's dark/light choice can layer on top of, rather than replace, the surface identity — this is an inference based on standard `data-theme` architecture, not something any source addressed for a role-based-skin scenario specifically.
- If the team wants owner/auth (currently fixed light glass) to also support a dark option (or diner/staff to support light), the `next-themes`-style pattern (cookie or localStorage + `data-theme` + inline/server-set attribute before paint) transfers directly; the main new work is defining a second token set (dark-mode equivalents of the light-glass palette, and light-mode equivalents of the dark-glass palette) rather than the theming *mechanism* itself, which is well-established.
- Given the app has no current persistence layer/cookie usage described, `localStorage` + inline blocking script in `<head>` is the lower-effort starting point; migrating to a cookie-based, Server-Component-rendered attribute is the more robust follow-up once/if SSR flash becomes a visible problem in production.

### Gaps
- No source specifically discusses reconciling a *fixed per-surface* theme scheme with a *user-togglable* one (this combination — different surfaces having different default "identities" plus an optional brightness toggle — is not a pattern any fetched source covered); the inference above is architecture-standard reasoning, not a cited best practice.
- No source was found benchmarking real-world flash duration/severity differences between the inline-script approach and the cookie+Server-Component approach specifically on Next.js 15/16 App Router (the version Shop AI uses); the qualitative claim ("eliminates flash entirely" for the cookie approach) comes from a single dev.to article, not a primary Next.js/Vercel doc — treat as a strong but unverified-by-primary-source claim.

## What are best practices for reducing reliance on inline `style={{}}` in React components, and how to prioritize which components to refactor first?

### Takeaway
Inline styles should be reserved for genuinely dynamic, per-instance values (e.g., a computed width, a live progress percentage); anything static or repeated belongs in CSS Modules/utility classes referencing shared design-token CSS variables, and small teams should prioritize refactoring by extracting tokens first, then the highest-repetition/highest-visibility components (buttons, inputs, layout containers) before long-tail one-off screens.

### Cited Findings
- General guidance: "Inline styles should not be used unless absolutely necessary, as they make theming harder, limit CSS features like hover or media queries, and reduce code clarity." — [rtcamp: Styling Best Practice for React-based projects](https://rtcamp.com/handbook/react-best-practices/styling/)
- Token-driven consistency argument: "When every Button, Card, and Input references the same token, you guarantee visual consistency across your application, whereas manual color values inevitably drift over time as different developers hard-code slightly different shades." — [UXPin: Managing Global Styles in React with Design Tokens](https://www.uxpin.com/studio/blog/managing-global-styles-in-react-with-design-tokens/)
- Recommended architecture: "CSS modules or external stylesheets are ideal for static styles, where you define styles in a separate CSS file and reference tokens like `var(--color-primary)`," while dynamic/state-driven values (e.g. theme switching) are better handled via a `data-theme` attribute plus CSS variable overrides than via inline style objects computed in JS — [UXPin](https://www.uxpin.com/studio/blog/managing-global-styles-in-react-with-design-tokens/); [Handoffpro: design tokens react](https://www.handoffpro.dev/blog/design-tokens-react)
- CSS Modules specifically "eliminate naming conflicts and global scope issues, with the full language available" (media queries, pseudo-classes, etc., which plain inline `style` objects cannot express), at the cost of styles living in a separate file from the markup — [Generalist Programmer: CSS Modules vs Tailwind CSS](https://generalistprogrammer.com/comparisons/css-modules-vs-tailwind)
- Small-team prioritization framework: start with tokens (color + spacing scale) before touching components at all — "Teams that start with component libraries fail. Teams that start with tokens survive" — then a minimum viable set of ~3 shared atoms (Button, Input, Badge/Chip-equivalent) that "cover ~80% of typical UI surface area with minimal maintenance burden"; naming conventions should be locked down "at the 10-component threshold to prevent divergence later" — [Fordel Studios: Design Systems from Scratch: A Small Team Playbook](https://www.fordelstudios.com/research/design-systems-from-scratch-small-teams)
- Same source's explicit anti-pattern warning: don't build a full design system before shipping the product, and don't treat any single component library as a substitute for owning your own tokens — [Fordel Studios](https://www.fordelstudios.com/research/design-systems-from-scratch-small-teams)

### Inferences
- For Shop AI specifically, the existing utility classes (`.btn`, `.chip`, `.pill`, `.in`, `.switch`, `.meter`, `.modal`, `.toast`, `.kanban`, `.alert-banner`) already represent exactly the "shared atoms" tier the sources say to prioritize — the refactor opportunity is not building new components but auditing where inline `style={{...}}` duplicates what one of these classes should already express (color, padding, border-radius, font) versus where it's expressing genuinely one-off layout (flex/grid positioning for a specific screen), and only the former needs to move into a class/token.
- A practical prioritization order following the "highest repetition, highest visibility first" logic implied by the sources: (1) any inline style setting a color, font, spacing, or border value that duplicates an existing CSS variable (highest ROI, likely mechanical find/replace), (2) inline styles on the most-reused components (buttons, inputs, cards) across all three surfaces, (3) inline layout styles on the highest-traffic screens (diner ordering flow, owner dashboard) last, since one-off grid/flex layout is the most legitimate use of inline `style` and the lowest-value refactor target.
- CSS Modules would let the team keep per-component style co-location (similar ergonomics to what large `style={{}}` objects currently give) while gaining access to hover/media-query features inline styles cannot express — this is a smaller conceptual leap from the current pattern than adopting Tailwind's utility-in-JSX model, since it preserves "one stylesheet-like block per component" thinking.

### Gaps
- No source gave a quantitative method for deciding "how much inline style is too much" (e.g., a lint rule threshold); recommendations found are qualitative style guidance, not enforceable metrics. A lint rule (e.g., `react/forbid-component-props` style restrictions, or a custom ESLint rule flagging non-dynamic values in `style=`) was not covered in sources found and would need separate investigation if the team wants automated enforcement.

## What are best practices for responsive design QA across specific device classes (diner phone, owner desktop+sidebar, waiter phone, chef wide/mounted screen)?

### Takeaway
Best practice for a small team without dedicated QA is a lightweight combination of browser DevTools device emulation for day-to-day iteration, a multi-viewport-at-once tool (e.g., Responsively App) for quick visual comparison across the app's specific breakpoints, and — most importantly for this project, since the spec admits zero manual testing/screenshots have been done — simply executing a structured checklist (orientation, touch-target size, reflow, contrast) once per real target device class and capturing screenshots as evidence, before reaching for paid cross-browser cloud services.

### Cited Findings
- Recommended free/lightweight tooling: browser DevTools device emulation for different resolutions; Google's Mobile-Friendly Test or Responsinator to simulate how a site appears on various devices; and "Responsively App is an open-source tool that offers multi-device synchronized views for responsive design testing" — [Testsigma: 7 Top Tools for Responsive Web Design Testing](https://testsigma.com/tools/responsive-design-testing-tools/)
- Paid/cloud cross-browser options for more thorough coverage: BrowserStack, LambdaTest, TestCafe are cited as top tools, and "cloud-based solutions don't require the installation of any testing infrastructure, can be accessed from anywhere, and are easy to learn and use" — [Testsigma](https://testsigma.com/tools/responsive-design-testing-tools/)
- Checklist components to test explicitly: orientation (portrait/landscape) and reflow behavior on rotation; touch-target size and spacing for interactive elements; multi-browser consistency (Chrome, Firefox, Safari, Edge); and side-by-side screenshot comparison across environments to spot rendering discrepancies — a tool like "Beep" was cited for this screenshot-diff workflow — [Testsigma](https://testsigma.com/tools/responsive-design-testing-tools/) / synthesized from same source
- Accessibility should be folded into the same QA pass: "Test for WCAG compliance. Check color contrast ratios. Use screen readers for usability testing." — [Testsigma: 7 Top Tools for Responsive Web Design Testing](https://testsigma.com/tools/responsive-design-testing-tools/)
- Visual regression testing tools (Chromatic, Percy) are the recommended next step once a project has enough components to make manual before/after screenshot comparison unwieldy — [Fordel Studios: Design Systems from Scratch: A Small Team Playbook](https://www.fordelstudios.com/research/design-systems-from-scratch-small-teams) (recommended at a "20+ components" threshold, alongside Chromatic/Percy specifically)

### Inferences
- Given the spec's own admission that manual testing on phone/tablet/desktop was never done and no screenshots exist, the lowest-effort, highest-impact first step is not new tooling at all — it's simply running the app once on the actual target device classes (a real or emulated 390px phone for diner/waiter, a desktop browser at a typical laptop width for owner, and whatever the "chef mounted screen" resolution actually is) and saving screenshots as a baseline; this converts "not yet done" into at least one verified snapshot per surface at near-zero cost, and only after that baseline exists does investing in Responsively App or a visual-regression tool become worthwhile.
- Because Shop AI's four surfaces map to genuinely different device classes rather than just breakpoints of one responsive layout (diner/waiter = phone, owner = desktop+sidebar, chef = wide/mounted display), the checklist should be organized per-surface rather than per-breakpoint — e.g., "diner" QA should specifically check the glass theme's contrast and backdrop-filter performance on a real low/mid-range phone (per the glassmorphism findings above), while "chef" QA should check large-display legibility and any auto-scaling/zoom behavior at a wide aspect ratio, which is a different concern set than mobile phone QA.
- The `prefers-reduced-transparency` and contrast-under-glass checks from the glassmorphism section should be added as explicit line items in this QA checklist for the diner/staff (dark glass) and owner/auth (light glass) surfaces, since generic responsive-QA checklists found in research don't call out glass-specific contrast testing — that gap needs to be filled by combining the two research areas.

### Gaps
- No source gave device-class-specific guidance matching Shop AI's unusual mix (phone/desktop-with-sidebar/wide-mounted-screen) — all sources address generic "mobile/tablet/desktop" responsive testing, not a "kitchen-mounted display" class; no dedicated guidance for QA-ing kiosk/mounted-display web UIs was found and would need a separate targeted search if needed.
- No specific browser/OS combination recommendations (e.g., which iOS/Android versions are still worth testing in 2026) were retrieved.

## Are there lightweight ways to introduce a design-token system (spacing scale, type scale, color roles) without a full framework migration?

### Takeaway
Yes — a small, single-platform project like Shop AI can get most of the benefit of a "real" design-token system just by formalizing its existing CSS custom properties into a documented, semantic token layer (a handful of color roles, a 4px-based spacing scale, a 5-6 step type scale built off a fixed ratio), with no build tooling, no Style Dictionary, and no Storybook required until the component count grows well past where the project is today.

### Cited Findings
- "If you're building a single-platform product with a small team, a well-maintained set of CSS variables or SCSS variables may be sufficient... design tokens become valuable when you maintain multiple platforms, support theming (e.g., dark mode), or need to keep a design system consistent across teams and products at scale." — [search synthesis citing UXPin: What Are Design Tokens? A Complete Guide](https://www.uxpin.com/studio/blog/what-are-design-tokens/)
- Concrete minimum-viable token set for a 2-5 person team: color + spacing tokens (4px base, multiples of 4), a typography scale of 5-6 sizes with line-heights, three core atoms (Button in ~3 variants, Input, Badge), and a single `tokens.md` file documenting every token (explicitly recommended so AI coding tools/new contributors don't invent ad hoc values) — [Fordel Studios: Design Systems from Scratch: A Small Team Playbook](https://www.fordelstudios.com/research/design-systems-from-scratch-small-teams)
- "Teams that start with component libraries fail. Teams that start with tokens survive." — [Fordel Studios](https://www.fordelstudios.com/research/design-systems-from-scratch-small-teams)
- Typographic scale technique: pick a base size (usually the smallest text) and multiply by a fixed ratio (e.g., 1.2 = "minor third") to generate the rest of the scale, rounding to a multiple of 4px; "Design tokens are perfect for creating proportional typographic scales because tokens can reference other tokens' values" and the same ratio can drive the spacing scale too — [UX Collective: Mastering typography in design systems with semantic tokens and responsive scaling](https://uxdesign.cc/mastering-typography-in-design-systems-with-semantic-tokens-and-responsive-scaling-6ccd598d9f21); [Penpot blog: Using design tokens for a proportional typographic scale](https://penpot.app/blog/using-design-tokens-for-a-proportional-typographic-scale/)
- Token layering principle: "The Scale defines only relationships, proportions, and hierarchy, without being tied to roles, styles, or components. The Scale creates a stable framework for the system that can be adjusted or even completely replaced without destroying the architecture" — i.e., separate a raw numeric scale (spacing-1, spacing-2, font-size-1...) from semantic roles that reference it (color-surface, color-text-primary, space-card-padding) — [Penpot blog](https://penpot.app/blog/using-design-tokens-for-a-proportional-typographic-scale/)
- Escalation path only if/when the project grows: Style Dictionary (open-source token transformation engine from Amazon UX) for compiling tokens to multiple output formats, or Zeroheight's free token manager / Supernova as managed platforms — explicitly framed as options for when a design tool (Figma variables) needs to stay synced with code, not a starting requirement — [cssauthor.com: Design Token Management Tools 2025](https://cssauthor.com/design-token-management-tools/); [Fordel Studios](https://www.fordelstudios.com/research/design-systems-from-scratch-small-teams)

### Inferences
- Shop AI already has the raw ingredient (a `globals.css` with CSS custom properties for colors and two font stacks) — the "lightweight introduction" here is almost entirely a naming/documentation exercise rather than new infrastructure: split existing ad hoc variables into (a) a raw scale (e.g., `--space-1` through `--space-6`, `--font-size-1` through `--font-size-6`) and (b) semantic roles that reference the scale (`--color-surface-diner`, `--color-text-on-glass`, etc.), then add a short `tokens.md`/comment block enumerating them — this directly follows the "tokens.md for AI-tool context" recommendation and costs no build step.
- Because Shop AI has two visually distinct glass themes (dark/light) applied per surface, its "color roles" tier should explicitly separate role name from theme value from day one (e.g., `--text-primary` resolves differently under `.aurora-d`/`.gd` vs `.aurora-l`/`.gl`), which both formalizes the current deliberate per-surface split and sets up the infrastructure needed later if true user-togglable dark/light mode (previous question) is ever added — the same `data-theme`-style variable-swapping mechanism serves both needs.
- Given the project's small size, deferring Style Dictionary/Storybook/visual-regression tooling (per Fordel Studios' phase thresholds of ~10-20+ components) is appropriate now and should be revisited only if the component count or team size grows meaningfully.

### Gaps
- No source addressed token-naming strategy specifically for a codebase with *two independent hardcoded themes* (as opposed to one theme or a light/dark toggle pair) — the recommendation to key semantic tokens by surface-theme is an inference, not a cited pattern from any source found.
- No source gave a concrete opinion on whether a project of Shop AI's exact size (~120 lines of CSS, a fixed utility-class vocabulary) should adopt Style Dictionary now vs. later beyond the general "10-20+ components" heuristic, which is itself from a single source (Fordel Studios) rather than corroborated across multiple.
