# Multilingual and Accessibility UX Best Practices — English/Thai/Burmese Restaurant Chatbot

## What are best practices for setting the `lang` attribute and other document-level accessibility signals in a client-rendered app where the user picks their language after page load, for both screen-reader correctness and SEO?

### Takeaway
WCAG 3.1.1 requires the page's default language to be programmatically determinable via the `lang` attribute on `<html>`; in a client-side app this means updating `document.documentElement.lang` (and `dir` if relevant) the moment the user's language selection changes, not leaving it hardcoded. The W3C's own SC 3.1.1 understanding document does not directly address dynamic SPA switching, so the "update it in a layout effect" pattern is practitioner best practice, not literal WCAG text. Separately, for SEO/hreflang, client-injected signals are unreliable because crawlers frequently don't execute JS — hardcoding `lang="en"` and expecting client-side language switching to help SEO in an SPA won't work without server-rendered signals or distinct per-language URLs.

### Cited Findings
- "SPAs should update document.documentElement.lang (and dir) when locale changes... set document.documentElement.lang when the route or locale changes" — [TOPdesk Tech Blog](https://techblog.topdesk.com/accessibility/language-and-accessibility-on-the-internet/)
- Setting `lang` via JS shortly after a DOM update generally lands in time for assistive tech; one source frames it as "a gap of approximately 100 milliseconds between adding an HTML element to the DOM and the screen reader reading it" — [Craig Abbott](https://www.craigabbott.co.uk/blog/2022/using-the-language-attribute-to-make-your-website-accessible/)
- SC 3.1.1 (Language of Page, Level A): "the default human language of each web page can be programmatically determined," implemented via the `lang` attribute on the HTML element; HTTP headers are only an advisory technique — [W3C Understanding SC 3.1.1](https://www.w3.org/WAI/WCAG22/Understanding/language-of-page.html)
- Confirmed gap in the primary source itself: the W3C Understanding document for SC 3.1.1 does not address dynamic language switching after page load or client-rendered apps — [W3C Understanding SC 3.1.1](https://www.w3.org/WAI/WCAG22/Understanding/language-of-page.html)
- SC 3.1.2 (Language of Parts, Level AA): any passage that switches language from the page default must be individually tagged with `lang` (e.g. `<span lang="th">`) so screen readers switch voice/pronunciation — [Silktide](https://silktide.com/accessibility-guide/the-wcag-standard/3-1/readable/3-1-2-language-of-parts/)
- Without lang tagging on embedded foreign-language text, "a screen reader set to English will attempt to pronounce [it] using English phonetics — producing garbled, incomprehensible output" — [getstark.co](https://www.getstark.co/wcag-explained/understandable/readable/language-of-parts/)
- SPA SEO: "Most crawlers, including AI search engines, don't execute JavaScript and receive the initial HTML response without hreflang signals... the initial HTML response contains a basic head, an empty div, and a script bundle, with no metadata added after hydration — including hreflang tags" — [Prerender.io](https://prerender.io/blog/how-to-optimize-single-page-applications-spas-for-crawling-and-indexing/)
- Recommended SEO pattern for multilingual sites is distinct per-language URLs (e.g. `/en/about`, `/th/about`) with server-rendered (not client-injected) hreflang tags, and every hreflang cluster must be fully reciprocal or Google treats it as invalid — [Digital Applied, International SEO Hreflang & Multilingual Guide](https://www.digitalapplied.com/blog/international-seo-hreflang-multilingual-guide)

### Inferences
- For Shop AI's diner UI, the fix is to call `document.documentElement.lang = <selected lang code>` (and re-set it on every language switch) in a layout effect keyed to the language-switcher state — this is the standard SPA pattern and lands in time for most screen readers, per the sources above.
- Because Shop AI has no separate localized routes (language is a client-side per-session choice), the hreflang/SEO angle is largely moot for the diner ordering UI itself — it isn't content search engines rank across languages. But the pre-interaction SSR/first-paint `<html lang>` should still default to a sensible value (not a permanent hardcoded `"en"` with no runtime correction), then be corrected client-side once the diner picks a language.
- AI-generated chat replies that mix scripts in one bubble (e.g., an English brand/dish name inside a Burmese sentence) should wrap the foreign-language span in its own `lang` attribute per SC 3.1.2 — this is a separate, finer-grained fix from the page-level `lang` correction.

### Gaps
- No source directly confirms screen-reader behavior when `lang` is changed many times in one session (toggling en/th/my repeatedly) — most guidance addresses locale set once per route/session, not frequent runtime switching.
- Findings on dynamic `lang` updates in SPAs come from practitioner blogs, not normative WCAG text — flag as good-practice inference, not a literal WCAG requirement.

## What are known font-rendering and typography pitfalls for Burmese and Thai script on the web — line-height, font-fallback ordering, digit rendering, and common mistakes?

### Takeaway
Both Burmese and Thai need substantially taller line-height than Latin text because diacritics/vowel signs/tone marks stack above and below the base consonant; getting this wrong is a well-documented, recurring bug (overlapping glyphs, clipped stacked marks). Font-fallback order and shaping-engine compatibility are separately fragile. Digit choice differs sharply between the two languages: Thai has largely moved to Arabic numerals for everyday/commercial use, while Burmese still commonly uses native digits — a blanket "use native digits for non-Latin scripts" rule is wrong across these two languages.

### Cited Findings
- "Thai text needs much larger line heights relative to font size than English... vertical stacking of diacritics, vowels, and tone marks above and below consonants, necessitating greater interline distance than in Latin scripts to prevent overlap between lines" — [Thai typography, Wikipedia](https://en.wikipedia.org/wiki/Thai_typography)
- Fallback fonts should share (not shrink) the root font's line-height: "If the line height of English is bumped up, that of Thai text should also increase proportionally and certainly should not be reduced to match the English" — [W3C, Typeface styles & font fallback](https://www.w3.org/International/articles/typography/fontstyles.en.html)
- "Falling back to a different writing style could affect the identity of the text, and a font designed for one Thai orthography may not cover all the glyphs needed for another" — [W3C, Typeface styles & font fallback](https://www.w3.org/International/articles/typography/fontstyles.en.html)
- "Thai is far more complex than Latin scripts, relying on shaping engines, ligatures, and contextual forms, and requires entire blocks intact to render correctly. Cross-browser rendering should be checked, as some Thai fonts may appear differently in Safari versus Chrome" — [DeveloperUX, Typography Challenges in Multilingual Design](https://developerux.com/2025/03/07/typography-challenges-in-multilingual-design/)
- For Burmese: "engineers need guidelines on spacing and line height specific to Burmese script behavior"; for services using embedded font files for Burmese, "some line-heights and font-sizes cause text to overlap" — [1StopAsia, Burmese Production Guardrails](https://www.1stopasia.com/blog/burmese-production-guardrails-script-rendering/)
- "The complex features of the Burmese script have caused many problems in rendering on computers. It is always [a] tricky script to get right with harfbuzz" — [GitHub, openmaptiles/fonts issue #14](https://github.com/openmaptiles/fonts/issues/14)
- Wikipedia's own Myanmar-script stylesheet uses "100% line-height" with a font stack of "Pyidaungsu, Myanmar Text, Myanmar3, Padauk, and Noto Sans Myanmar" — real-world practice stacks *multiple* Myanmar-capable fonts, and treats Myanmar line-height as a separately-tuned value rather than inheriting the page default — [Wikipedia, Template:Script/styles myanmar.css](https://en.wikipedia.org/wiki/Template:Script/styles_myanmar.css)
- Digits — Thai: "professional Thai localization uses Arabic numerals for most business and commercial writing, while traditional Thai numbers are used only in formal business situations including legal documents and official contracts... use of Thai digits is less common in Thailand than it once was" — [SEAtongue, Thai Localization Guide](https://seatongue.com/resources/language-center/thai-localization-guide/)
- Digits — Burmese: "Myanmar stands out as an exception to broader trends in Asia... record-keeping still largely done in Burmese numerals, and traditional Burmese numerals still widely used in literature, newspapers, and handwriting. This contrasts with Thailand, Cambodia, and China, which increasingly prefer Hindu-Arabic forms in daily use" — [Fifty Viss, "Will Burmese numerals ever fall out of fashion?"](https://viss.wordpress.com/2015/06/07/will-burmese-numerals-ever-fall-out-of-fashion/) (note: this specific source is from 2015 — dated; treat the "still widely used" framing as directionally consistent with newer snippets but not itself current data)
- Noto Sans Myanmar is part of Google's Noto family (goal: no missing-glyph "tofu" boxes across scripts); "the Noto collection has separate fonts for different scripts, so you should only select fonts for the languages that your website actually uses... you can specify a family stack: multiple font families separated by commas" — [Google Fonts / Noto, "Use Noto"](https://fonts.google.com/noto/use)

### Inferences
- Shop AI's 1.9 line-height for Burmese chat bubbles (vs. 1.5 default) is directionally aligned with real-world practice (Wikipedia separately tunes Myanmar line-height rather than inheriting the default), but should be verified empirically against actual stacked-vowel/tone-mark sequences, not just plain text, since overlap bugs are specifically about tall marks.
- Thai bubbles are not described as having a bumped line-height in Shop AI's current setup — only Burmese is. Given the sourced claim that Thai also needs much larger line-height than Latin (same underlying cause: stacked tone marks/vowels), this looks like a likely gap: Thai bubbles may need a comparable (not necessarily identical) line-height bump, not just Burmese.
- Because Noto Sans Myanmar/Thai are loaded only as *fallback* fonts globally, fallback *ordering* matters — the Latin primary font must not sit ahead of the Myanmar/Thai fallback for characters it doesn't cover. The Wikipedia example also shows production Myanmar sites often stack several Myanmar-capable fonts (not just one Noto font) for better device/browser coverage; a single-fallback-font setup is simpler but less resilient than that pattern.
- Digit rendering should not follow a single blanket rule: Thai commercial/UI copy conventionally defaults to Arabic numerals, while Burmese has stronger real-world persistence of native digits. Shop AI's Burmese-digit price rendering is plausible as a deliberate, defensible choice, but the same treatment should not be assumed correct for Thai prices without checking current Thai-market convention — sources suggest Arabic numerals are the safer default there.

### Gaps
- No source gave a specific numeric line-height recommendation for Burmese beyond Wikipedia's Myanmar-specific 100%-line-height CSS value and generic "needs to be larger" guidance — could not confirm whether 1.9 is optimal, only that bumping it is directionally correct.
- No current (2025/2026) survey data found on what share of Thai commercial/consumer apps still show native Thai digits specifically for prices (vs. general text) — the sourced claim is about Thai localization broadly, not menu/price UI specifically.
- Did not fetch Google/Noto's own documentation site (notofonts.github.io) directly; Noto findings rely on search snippets rather than a full primary-source read.

## What WCAG 2.1/2.2 guidance is specifically relevant to complex/non-Latin scripts and multilingual switching (language-of-parts, text spacing, target size)?

### Takeaway
Three groups of success criteria are directly relevant — 3.1.1/3.1.2 (Language of Page/Parts) for correct `lang` tagging, and 1.4.8 (AAA)/1.4.12 (AA) for text/line spacing. WCAG explicitly builds exception logic for scripts that don't use certain text-style properties (e.g., CJK word-spacing), a principle the working group is still actively debating extending more clearly to other non-Latin/non-CJK scripts. There is no Myanmar- or Thai-specific WCAG success criterion — only these general criteria applied per-script.

### Cited Findings
- SC 3.1.1 Language of Page (Level A) and SC 3.1.2 Language of Parts (Level AA): page-level `lang` must be programmatically determinable, and any content section in a different language than the page default must be individually tagged — [W3C Understanding SC 3.1.1](https://www.w3.org/WAI/WCAG22/Understanding/language-of-page.html), [Silktide on 3.1.2](https://silktide.com/accessibility-guide/the-wcag-standard/3-1/readable/3-1-2-language-of-parts/)
- SC 1.4.8 Visual Presentation (Level AAA) recommends "line spacing (leading) is at least space-and-a-half within paragraphs, and paragraph spacing is at least 1.5 times larger than the line spacing," and separately limits line width to "no more than 80 characters or glyphs (40 if CJK)" — WCAG already treats CJK-class scripts differently for line-length even at the AAA level — [accessibility.build summary of W3C Understanding SC 1.4.8](https://accessibility.build/wcag/1-4-8)
- SC 1.4.12 Text Spacing (Level AA) includes an explicit exception: "Human languages and scripts that do not make use of one or more of these text style properties in written text can conform using only the properties that exist for that combination of language and script" (e.g., CJK doesn't use Latin-style inter-word spacing) — [Dequeuniversity](https://dequeuniversity.com/resources/wcag2.1/1.4.12-text-spacing), [W3C Understanding SC 1.4.12](https://www.w3.org/WAI/WCAG21/Understanding/text-spacing.html)
- Even where the exception applies, authors "should still allow for adjustments consistent with this success criterion, even though users will probably not use these settings in these languages" — i.e., content shouldn't visually break under a forced spacing override — [W3C Understanding SC 1.4.12]
- There is active, unresolved W3C working-group discussion that current wording needs revision for non-Latin/non-CJK scripts specifically: an open GitHub issue titled "Text spacing exception unclear" and another on "Letter/Word spacing for CJK languages" note that "changes are necessary to 1.4.8 and 1.4.12 to accommodate non-Latin scripts" — [w3c/wcag issue #3338](https://github.com/w3c/wcag/issues/3338), [w3c/wcag21 issue #677](https://github.com/w3c/wcag21/issues/677)

### Inferences
- WCAG's CJK exception logic (for scripts lacking word-spacing) doesn't neatly cover Thai or Burmese, which aren't CJK but also don't use Latin-style word spacing (Thai in particular has no spaces between words within a sentence). Shop AI should still keep letter-spacing/line-height adjustable where meaningful, and treat literal "word spacing" controls as not applicable to Thai body text — consistent with the exception's spirit even though Thai isn't explicitly named in the criterion text.
- Because no Myanmar/Thai-specific SC exists, Shop AI's 1.9 line-height for Burmese is effectively filling a gap WCAG leaves at the general "AAA, space-and-a-half" baseline (i.e., 1.5) — 1.9 already exceeds that general baseline, which is reasonable given documented overlap issues, but should still be validated against SC 1.4.12's requirement that user-forced spacing overrides not break the layout.

### Gaps
- No WCAG technique or W3C i18n article was found giving concrete numeric line-height guidance specifically for Burmese or Thai — no official "use X line-height for Myanmar script" success criterion or technique exists; the 1.9/1.5 split in Shop AI is a project-level empirical choice, not one traceable to an explicit standard.
- Could not confirm within the research budget whether WCAG's Target Size criteria (2.5.8 AA / 2.5.5 AAA) have any documented interaction with Southeast-Asian script glyph density (e.g., whether denser glyphs push teams toward larger tap targets in a language switcher) — no source on this was found; flagged as unresearched rather than "no such guidance exists."

## Is Zawgyi vs. Unicode still a practical concern for Burmese text in 2025-2026, and what's the standard mitigation?

### Takeaway
Yes — Zawgyi remains a real, if declining, practical concern. Myanmar's official Unicode migration ("U-Day") happened October 1, 2019, but the transition was disrupted by the 2021 coup, older/preloaded devices and legacy content still exist in Zawgyi, and the cross-encoding garbling problem has not fully disappeared. The standard mitigation is automated Zawgyi/Unicode detection (commonly ML-based, e.g., Google's `myanmar-tools`) plus conversion at input/ingestion time — not manual user-facing handling.

### Cited Findings
- Myanmar's government designated October 1, 2019 as "U-Day," the official switch to Unicode, with one developer's estimate of ~2 years for full transition — [Wikipedia, Zawgyi font](https://en.wikipedia.org/wiki/Zawgyi_font)
- "The transition has been somewhat complicated by the effects of the 2021 Myanmar coup d'état," and "content written in Unicode appears garbled to Zawgyi users and vice versa" — [Wikipedia, Zawgyi font](https://en.wikipedia.org/wiki/Zawgyi_font)
- Zawgyi "remains a practical concern because smartphone manufacturers like Samsung and Huawei preloaded it, and content creators often post in both formats simultaneously to reach diverse audiences" — [Wikipedia, Zawgyi font](https://en.wikipedia.org/wiki/Zawgyi_font)
- Google's `myanmar-tools` library exists specifically to "detect whether a string is Zawgyi or Unicode" using a machine-learning classifier (not hand-coded rules) "to avoid false positives in similar scripts like Shan and Mon," returning a 0-1 probability score. Detection is available in C++, Java, JS (Node + browser), PHP, Ruby, Dart, Go, Python, Swift, and C#; conversion is currently available in Java and JS, with ICU covering conversion in other languages — [github.com/google/myanmar-tools](https://github.com/google/myanmar-tools)
- Recommended integration pattern: run the detector on input text; if the Zawgyi-probability score exceeds a chosen threshold, convert to Unicode. Suggested thresholds are asymmetric depending on whether missed detections or false conversions are costlier (e.g., ~0.05 vs ~0.95) — [github.com/google/myanmar-tools](https://github.com/google/myanmar-tools)
- Multiple Zawgyi<->Unicode converter tools remain actively maintained/available as of 2024-2025 (e.g., a "2024 Update" and a "2025" tool), circumstantial evidence of continued end-user demand — [MyanmarHouse font converter](https://www.myanmarhouse.com.mm/en/tools/myanmar-font-converter), [zawgyitounicodeconvertor.com](https://zawgyitounicodeconvertor.com/)

### Inferences
- For Shop AI, the exposure is specifically at free-text input points from diners/owners typing Burmese (e.g., a custom order note, or an owner-entered menu item) on an older or legacy-configured device/keyboard that still produces Zawgyi-encoded bytes. Anywhere Burmese text is only ever chosen from the team's own fixed `my` UI dictionary, there is no Zawgyi risk, since the team controls that text as Unicode already.
- The standard, low-effort mitigation for a small team matches exactly what the product spec called for: run detection (e.g., `myanmar-tools`, which has a JS build usable in a Next.js app) on any free-text Burmese input at the point of ingestion, and normalize/convert to Unicode before storage. This avoids needing a UI-facing "which font/keyboard are you using" prompt and keeps stored data (menu items, chat transcripts) consistently in Unicode.
- This is a legitimate near-term backlog item, not an obsolete concern — Myanmar is one of the few remaining markets globally where this encoding split is still a live, documented problem in 2025-2026 per the sources found.

### Gaps
- No 2025/2026-dated, quantitative statistic was found (e.g., "X% of Myanmar devices still default to Zawgyi") — the most concrete data point (U-Day, 2019, ~2-year transition estimate) is now stale, and the Wikipedia article is itself flagged in-page as needing updates. The "still a concern" conclusion rests on qualitative evidence (coup disruption, legacy-preloaded devices, actively maintained converter tools), not a hard current adoption percentage.
- Could not independently verify (beyond vendor/tool-site framing) the specific claim that Zawgyi content reduces search visibility — treat as plausible but unverified.

## Best practices for deciding which parts of an app to localize first when resources are limited — is it standard for admin dashboards to stay in one language while the customer app is multilingual?

### Takeaway
Standard i18n practice separates internationalization (engineering infrastructure — externalized strings, locale-aware formatting, `lang`/dir handling) from localization (the ongoing content/translation effort), builds the infrastructure everywhere up front, and then sequences translation work by user-facing impact. It is common and broadly accepted for admin/back-office interfaces to stay in a single language (often English) longer than the customer-facing surface — but the sourced guidance frames this as *deferred* scope, not permanently excluded scope.

### Cited Findings
- "Consumer apps often localize a focused surface area with a handful of screens and a few hundred strings, while SaaS products are different with larger and more complex UIs including dashboards, settings pages, onboarding flows, and billing" — dashboards are recognized as a larger, separate, and often later-stage localization effort compared to core consumer screens — [SimpleLocalize, "Internationalization for SaaS teams"](https://simplelocalize.io/blog/posts/i18n-for-saas-teams/)
- A comprehensive localization scope "includes visible UI labels, empty states, error messages, onboarding, account emails, push notifications, transactional SMS, payment messages, legal notices, help content, admin screens, dashboards, reports, exports, and text in templates" — admin screens/dashboards are explicitly named as within eventual full scope, not excluded — [SimpleLocalize, "The complete technical guide to i18n"](https://simplelocalize.io/blog/posts/internationalization-guide-software-localization/)
- "i18n is an engineering investment made once and maintained, while localization is an ongoing operational process that depends on that i18n investment being in place. Many teams treat internationalization as an afterthought rather than a priority and get stuck in a reactive cycle" — [SimpleLocalize, "The complete technical guide to i18n"](https://simplelocalize.io/blog/posts/internationalization-guide-software-localization/)
- Recommended sequencing: establish i18n infrastructure early so you can "prioritize translation efforts strategically later, starting with your highest-impact customer-facing features while keeping admin interfaces in scope within your broader localization roadmap" — [SimpleLocalize, "Internationalization for SaaS teams"](https://simplelocalize.io/blog/posts/i18n-for-saas-teams/)

### Inferences
- Shop AI's current split (diner-facing UI localized in en/th/my; owner dashboard English-only) matches the commonly observed real-world sequencing pattern (customer-facing first, admin/dashboard deferred) and is a defensible resourcing decision for a small team — *provided* the restaurant owners/staff who actually use the dashboard are comfortable reading English. That assumption is a product/market question the team should explicitly verify, not an accessibility-best-practice question the sources resolve — none of the guidance says English-only dashboards are fine regardless of who operates them.
- The sourced material draws a sharp line between infrastructure and content: Shop AI should build (or keep) the *infrastructure* for dashboard localization (an i18n dictionary mechanism analogous to the diner-facing `en`/`th`/`my` dictionary) even while deferring actual owner-facing translation, so that adding `th`/`my` dashboard strings later is a translation task, not a re-architecture.
- No source says "it is fine to never localize admin dashboards" — the closest framing is "admin screens... within your broader localization roadmap," i.e., deferred but still expected eventually. Treat the English-only dashboard as a documented, time-boxed decision, not a permanent architectural stance, especially since restaurant owners in Thailand/Myanmar are a named stakeholder group for this product.

### Gaps
- No authoritative, named case study of a restaurant-tech or hospitality SaaS company specifically that localized diner apps before admin/back-office dashboards was found — the guidance found is generic SaaS i18n advice, not hospitality-vertical-specific.
- No data found on how commonly restaurant owners/staff in Thailand or Myanmar are comfortable operating an English-only back-office tool — this is a product-research question outside the scope of sources found, and should be validated with actual users rather than assumed.

## What UX patterns exist for gendered/polite language variation in UI copy (Thai/Burmese politeness particles) — should this be automatic, user-configurable, or avoided?

### Takeaway
Thai and Burmese grammatically encode speaker gender and formality through sentence-final particles, which forces a real design choice: pick one gendered voice for the whole product, make it configurable, or aim for a neutral/particle-light register. Sourced Thai-localization guidance frames "always-on gendered particles" as a decision requiring deliberate, explicit product ownership (it assigns a perceived gender identity to the brand voice), while broader UX/AI-ethics literature on gendered chatbots warns against unreflective default-gendering and stereotype reinforcement — though that broader literature is about the *assistant's own persona* gender, not about the assistant inferring and adapting to an individual *customer's* gender.

### Cited Findings
- In Thai, "khrap is used by male speakers; kha by female," and in formal settings gender-specific particles are used at the end of the sentence for politeness, "posing a challenge during the localization process. Selecting one assigns a perceived gender identity to your brand voice, which requires a deliberate decision before translation begins" — [Thiantawan, "UX Writing Challenges: Inclusive Pronouns in Thai Localization," Medium](https://medium.com/@thiantawan/ux-writing-challenges-inclusive-pronouns-in-thai-localization-3cb659563277)
- "Professional Thai often encodes respect, formality, and hierarchy through word choice, sentence structure, and particles, which matters in customer support where tone errors can be perceived as rude or overly casual" — [SEAtongue, Thai Localization Guide, via search synthesis](https://seatongue.com/resources/language-center/thai-localization-guide/)
- On chatbot gendering broadly: "Social cues like gender are important design features of chatbots, though choosing how to implement them is challenging... researchers have proposed chatbot social cue configuration systems that help engineers make justified design decisions grounded in empirical research" — [ResearchGate, "Gender Bias in Chatbot Design"](https://www.researchgate.net/publication/337403025_Gender_Bias_in_Chatbot_Design)
- "Many well-known virtual assistants like Siri, Alexa, and Cortana are styled as female... gendering them female reinforces stereotypes that assistants should be female by default"; one named study found a chatbot "was perceived as using sexist language and proposing stereotyped activities" — [Gendered Innovations, Stanford, "Virtual Assistants and Chatbots"](https://genderedinnovations.stanford.edu/case-studies/virtual.html)
- Design recommendation: "avoid gender-related inferences that draw conclusions from biased premises... emphasize overarching topics like skills, goals, and knowledge rather than gender... When asking about gender is necessary, use gender-friendly language that allows users to skip the question, choose multiple options, or write in custom options" — [Atomic Object, "3 Ways to Remove Gender Bias from Early UX Design Phases"](https://spin.atomicobject.com/2020/10/27/gender-bias-ux-design)

### Inferences
- The chatbot-gender-bias literature above is about *inferring/assigning a persona gender to the assistant itself* — a distinct question from Shop AI's actual described behavior (the AI adapting phrasing/particles based on, presumably, the diner's gender or the grammatical requirements of polite address). No source directly addressed "AI infers the customer's gender and adapts its own grammatical particles accordingly" as a named pattern — flagged as a gap below.
- Given the Thai-localization source's explicit framing ("requires a deliberate decision before translation begins"), the more defensible pattern for Shop AI is likely: treat particle/politeness-level choice as a deliberate *product/brand* decision (e.g., a neutral-polite register, or a restaurant-configurable default), rather than having the AI *infer* an individual diner's gender from their name/text and gender its own replies accordingly — inferring gender from limited signals is exactly the "gender-related inferences from biased premises" pattern the UX-bias literature warns against.
- A defensible middle path from the combined findings: keep formality/politeness level always-on (less fraught, and expected as a respectful default in Thai/Burmese service contexts), but avoid automatically *gendering* the AI's own speech based on an inferred customer gender. If gendered self-reference is grammatically unavoidable (the AI must pick a male or female particle for itself), treat that as a one-time configurable brand-voice setting rather than a per-message inference.

### Gaps
- No source specifically discusses a chatbot or ordering-app pattern for *inferring the customer's* gender to select Thai/Burmese response particles (as distinct from the AI's own persona gender) — this appears to be an under-documented design question; the closest analogous guidance (skippable/optional gender fields, avoiding inference from biased signals) comes from general chatbot-gender-bias literature, not Thai/Burmese-particle-specific sources.
- No UX research was found specifically recommending a shipped "user-configurable formality/politeness level" setting in a Thai/Burmese product — this remains an inference from adjacent literature, not a directly cited pattern.
- No source addresses whether gendering AI replies based on inferred diner gender carries elevated risk specifically in a *public-facing restaurant chatbot* context (vs. general chatbot literature) — plausible extrapolation, not a directly cited finding.
