# Shop_Ai: Detailed Feature Plan (Web Version)

AI menu chatbot for restaurant owners. Diners scan a QR code and chat with an assistant that knows only that restaurant's menu. Owners manage the menu and see what diners ask.

Source: market research report (diner pain points, owner adoption barriers, competitor gaps). Priority tags: **P0** = MVP, **P1** = Phase 2, **P2** = Phase 3.

---

## 1. Diner experience (public page, no login, no app)

Route: `/r/[restaurant-slug]?t=[table]`

### 1.1 Menu browsing (P0)
Why: 66% of diners want photos, 26% complain about tiny text, 90% dislike today's QR menus.
- Mobile-first layout, large readable text (min 16px), sticky category tabs, search box.
- Dish card: photo, name, price, short description, dietary badges (vegan, halal, spicy, gluten-free), allergen icons.
- Dish detail sheet: full description, ingredients, allergens, "Ask AI about this dish" button.
- Sold-out items greyed out with "Sold out today".
- Loads in under 2 seconds on 4G; images lazy-loaded and resized.
- Menu cached in the browser (PWA / service worker) so it still opens with weak signal.
- Filters: dietary tag, allergen exclusion ("hide dishes with nuts"), price range.
- Acceptance: menu usable without ever touching the chat.

### 1.2 AI chat assistant (P0)
- Floating chat button on every screen; opens a bottom sheet.
- Suggested starter chips: "What's popular?", "Vegetarian options", "Under $10", "No spicy".
- Handles: recommendations, budget limits, dietary needs, pairings, "what's in this dish", opening hours, FAQs (parking, Wi-Fi, invoices, private rooms).
- Streams the reply token by token; shows dish cards inline (tap to open detail).
- Answers only from the owner's data. If the info is missing: "I don't have that, please ask our staff."
- Conversation memory within the session only (no account).
- "Call staff" button always visible (P0), and a link back to the plain menu.
- Rate limit per session and per restaurant (see 5.3).

### 1.3 Allergen and dietary safety (P0, highest risk)
Why: chatbot misstatements create legal liability (Moffatt v. Air Canada).
- Allergen answers are built from structured fields, not free text generated by the model.
- Fixed wording for allergy questions: lists the dish's declared allergens, then "Our kitchen may handle other allergens. Please confirm with staff before ordering."
- Dishes with no allergen data show "Allergen info not provided" (never "safe").
- The AI may not say "safe", "guaranteed", or "allergy-free". Output check rejects those words and falls back to the template.
- The 14 EU allergens are the standard list (matches EU 1169/2011).
- Test set of allergen trap questions must pass 100% before launch.

### 1.4 Multilingual (P0 chat, P1 UI)
- AI replies in the language the diner writes in (auto-detect). **Launch languages (decided): Thai, Burmese (Myanmar), English.** Diner UI text, AI replies and owner dashboard all support these three. Burmese input may arrive as Zawgyi (old non-standard encoding still common in Myanmar) or Unicode: detect Zawgyi and convert to Unicode before it reaches the model (e.g. Rabbit/myanmar-tools detector), and display Unicode with a bundled Burmese web font (Noto Sans Myanmar) so it renders on every phone.
- P1: language switcher for the menu UI text; owner-entered dish names/descriptions translated once by AI and cached, owner can edit.
- Prices shown in the restaurant's currency; P1 adds approximate conversion for tourists.

### 1.5 Personalization within a session (P1)
- "For you" strip based on what the diner said in chat (e.g. likes spicy, no pork).
- Preferences held in browser storage only, no login, no personal data sent to the server.

### 1.6 Group, budget and pairing helpers (P1)
- "Plan a meal for 4 under $60", drink and dessert pairing, upsell suggestions phrased as help, not pressure.
- Owner can toggle upselling on/off.

### 1.7 Ordering, pay and bill split (P2, optional)
Commoditized; only build through an integration (Stripe / local QR payments like PromptPay, QRIS, KBZPay/Wave), not custom payments.
- P0 substitute: "Call staff" and a "Show my picks to waiter" list (diner builds a list, staff takes the order normally).

### 1.8 Fallback and offline (P0)
- If the AI service is down or the cap is hit, the chat shows a friendly message and the static menu keeps working.
- Cached menu shown when offline with an "Offline copy, prices may differ" note.

### 1.9 Feedback (P1)
- Thumbs up/down on each AI answer; optional "report a wrong answer" that flags it for the owner.

## 2. Owner dashboard (login required)

Route: `/dashboard`

### 2.1 Account and onboarding (P0)
- Email + password or Google login (Supabase Auth). Password reset.
- Setup wizard: restaurant name, slug, logo, currency, languages, opening hours, then menu upload. Target: first live menu within 30 minutes.
- One owner per restaurant at MVP; P1 adds staff roles (owner, manager, read-only).

### 2.2 Menu import by photo / PDF / manual (P0)
Why: menu entry is the top adoption barrier; ~70% of menus live in PDFs or print.
- Upload one or many photos, or a PDF. Camera capture on phone.
- Pipeline: upload -> OCR model -> LLM turns text into structured items (name, description, price, category) -> review screen.
- Review screen: side-by-side original image and extracted items, low-confidence fields highlighted, bulk edit, merge/split items, fix categories.
- Owner must confirm before publishing. Nothing goes live unreviewed.
- Also: manual add, CSV import (P1), copy from Google Sheet (P2).
- Acceptance: 90%+ items correct on a set of 10 real menus, or it doesn't ship.

### 2.3 Menu item management (P0)
- Fields: name (per language), description, price, category, photo, ingredients, allergens (14 checkboxes), dietary tags, spice level, prep notes, availability.
- AI suggestions for allergens/tags from ingredients, shown as suggestions the owner must approve (never auto-published).
- Drag-and-drop ordering of categories and items.
- Item variants and add-ons (size, extras) with price changes (P1).
- "Allergen data complete" progress meter per menu, since gaps weaken the safety feature.

### 2.4 Photos (P0 upload, P1 AI)
- Upload dish photos with automatic crop/compress.
- P1: AI-generated dish images for owners with no photography, clearly labelled "illustration" to avoid misleading diners.

### 2.5 Daily operations (P0)
- One-tap "Sold out today" toggle (86'd) that the chat respects instantly.
- Today's specials and promotions with start/end dates.
- Opening hours, holiday closures, temporary notices.
- Price edits apply immediately to menu and chat.

### 2.6 FAQ and shop rules (P0)
- Q&A list (parking, Wi-Fi, reservations, invoices, dress code, private rooms, delivery).
- Custom rules the AI must follow (e.g. "Don't discuss discounts", "No alcohol after 10pm").
- AI persona: tone (friendly / formal / playful), name, greeting message.

### 2.7 QR code tools (P0)
- Generate QR for the restaurant and per-table QR codes (with table number).
- Download PNG/SVG/print-ready PDF sheet, with table-tent template.
- Short URL, so codes never break when the menu changes.

### 2.8 Chat preview and testing (P0)
- "Test your assistant" panel in the dashboard, using the live data, so owners see what diners will see before publishing.

### 2.9 Insights (P1, main differentiator)
- Most-asked questions, grouped by topic (allergens, prices, vegetarian, hours).
- "Couldn't answer" list: questions the AI had no data for, with a one-click "add FAQ".
- Demand signals: "47 people asked for vegan options" (unmet demand).
- Popular and never-viewed dishes; views per dish; peak hours; languages used.
- Flagged answers from diner feedback for review.
- Weekly email summary to the owner.
- Privacy: store question text without any personal identifiers.

### 2.10 Billing (P1)
- Free plan: 1 location, capped chats/month. Pro (~$15-29/mo flat): higher cap, insights, more languages, remove branding. Multi-location later.
- Stripe subscriptions (or regional payment provider). No per-order commission, no per-table pricing.
- Usage meter visible in dashboard.

## 3. AI system

### 3.1 Answer pipeline (P0)
1. Receive question + session history.
2. Load restaurant data as JSON: menu, availability, hours, FAQs, rules, persona.
3. If the question is about allergens, run the templated allergen path (see 1.3).
4. Otherwise call the LLM with strict system prompt: answer only from data, never invent, reply in the diner's language.
5. Output checks: banned safety words, prices/ingredients mentioned must exist in the data, else fall back to a safe reply.
6. Log question and answer (no personal data) for insights.

### 3.2 Model setup (P0)
- OpenAI-compatible endpoint; model set by environment variable.
- Default chat model: **aisingapore/Gemma-SEA-LION-v4-27B-IT** (covers Thai, Burmese and English). Challenger in the bake-off: Qwen/Qwen3.8-27B (Apache-2.0). Route by detected language only if the bake-off shows Qwen is clearly better for English. Bake-off test set is Thai, Burmese, English only.
- OCR: typhoon-ai/typhoon-ocr1.5-2b for Thai menus; DeepSeek-OCR-2 / dots.ocr / Qwen3.8 vision for English and Burmese. Burmese OCR is the biggest unknown: test on real Myanmar menus in Phase 0, and if accuracy is under 90% use a vision LLM reading the photo directly plus a stronger manual-edit screen.
- Embeddings (only if needed for big menus/FAQs): intfloat/multilingual-e5-large.
- Prompt caching of the static menu portion to keep cost near 0.1 cent per chat.

### 3.3 Safety and quality (P0)
- Prompt-injection defence: diner text is treated as data; requests like "ignore your rules" are refused.
- Off-topic questions politely declined and steered back to the menu.
- Cost guard: max tokens per reply, max messages per session.
- Regression test set (30+ questions, several languages) run on every prompt or model change.

## 4. Platform and non-functional requirements

### 4.1 Architecture (P0)
- Next.js frontend and API routes, Supabase (Postgres, Auth, Storage), deployed on Vercel.
- Model calls only from the server; API keys never reach the browser.

### 4.2 Data model
- `restaurants` (id, owner_id, slug, name, currency, languages, hours, persona, rules)
- `categories`, `menu_items` (i18n names/descriptions, price, allergens[], dietary_tags[], ingredients, photo_url, available, sort_order)
- `specials`, `faqs`
- `chat_sessions` (restaurant_id, language, started_at), `chat_messages` (question/answer text, flagged, feedback)
- `usage_counters` (restaurant_id, month, chat_count)
- `menu_imports` (source file, OCR result, status)
- Row-level security: owners see only their own restaurant; the public page reads only published data.

### 4.3 Performance
- Public menu page under 2 s on 4G; first chat token under 2 s.
- Images resized and served through a CDN.

### 4.4 Privacy and compliance
- No diner login, no tracking cookies, no personal data collected in chat.
- Privacy notice link on chat sheet; data deletion on owner request.
- GDPR-friendly by design; allergen disclosure aligned with EU 1169/2011 and California SB 68 for later markets.

### 4.5 Accessibility and UX
- WCAG AA contrast, screen-reader labels, large touch targets, works on old Android phones.
- Right-to-left not needed at launch; Burmese (Unicode, Zawgyi converted) and Thai fonts must render correctly; test on low-end Android phones.

### 4.6 Reliability and monitoring
- Error tracking (Sentry), uptime check, log of AI failures and fallbacks.
- Daily database backup.

### 4.7 Security
- Owner-only routes protected; rate limiting and bot protection on chat endpoint; upload size and type limits; image files scanned for type.

## 9. University project on a MacBook Air M4 (replaces the GPU-server sizing)

Decision change: the project is a university project and the AI model runs on a MacBook Air M4 (unified memory, no separate GPU). The server-scale plan is dropped. All speeds below are estimates from memory bandwidth and typical Apple-silicon results, not measurements; measure them in Week 1.

### 9.1 What the laptop can run
Check your memory first (Apple menu > About This Mac). M4 Air memory is 16, 24 or 32 GB, shared by macOS, the browser, the database and the model. macOS lets the GPU use roughly 65-75% of it by default. M4 memory bandwidth is about 120 GB/s, and chat speed is roughly bandwidth / model size in memory (real results ~60-75% of that).

| Model (4-bit) | Size in RAM | Est. speed | Fits 16 GB | 24 GB | 32 GB | Role |
|---|---|---|---|---|---|---|
| aisingapore/Gemma-SEA-LION-v4-4B-VL (Thai, Burmese, English; reads images) | ~3 GB | 30-40 tok/s | yes | yes | yes | Default chat + menu-photo reading |
| Qwen/Qwen3.8-Flash-Next (3.8B; licence "Other", check terms) | ~3 GB | 30-40 tok/s | yes | yes | yes | Challenger in the test |
| aisingapore/Gemma-SEA-LION-v3-9B-IT (GGUF available) | ~6 GB | 15-18 tok/s | yes, tight with browser | yes | yes | Better answer quality, slower |
| mlx-community/gemma-3-12b-it-4bit (general multilingual) | ~8 GB | 10-13 tok/s | no (too tight) | yes | yes | Quality comparison only |
| 27B models (SEA-LION v4 27B, Qwen3.8-27B) | ~15-16 GB | 5-7 tok/s | no | too tight | possible, slow | Not practical, skip |

Recommended: run the model test with the 4B-VL, the 3.8B Flash and the 9B, and pick the smallest one that passes your Thai/Burmese/English test set. Small models make more mistakes with Burmese, which makes the grounding rules in section 1.3 and 3.1 more important, not less.

### 9.2 Expected performance for a demo (1-3 users at once)
- Prompt size: a 50-dish menu is ~3,000 tokens in English, maybe 6,000-9,000 in Burmese. Reading it without a cache takes ~10-40 s on an M4 (estimate, prefill ~150-300 tok/s for 4-9B). **Cache the menu once per restaurant** (llama.cpp prompt cache or mlx_lm prompt cache) so each question only processes the new ~100-300 tokens: first token in ~1-3 s.
- Answer of ~150 tokens: about 4-6 s with the 4B, 8-10 s with the 9B.
- Concurrency: the laptop serves one answer at a time well; 2-3 simultaneous chats will queue and slow down. Fine for a demo and class presentation, not for real users.
- Fanless Air: long benchmark runs throttle the chip. Keep the laptop plugged in, on a hard surface, and run tests in short batches.
- Memory budget example (24 GB): macOS 5 GB + browser/VS Code 4 GB + Postgres/Next.js 1 GB + model 6 GB (9B) + KV cache 1-2 GB = ~18 GB, OK. On 16 GB use the 4B.

### 9.3 CPU and other needs
- CPU: M4 has 10 cores (4 performance + 6 efficiency). The model runs on the GPU; the CPU handles Next.js, tokenization and the database, normally under 20% load.
- Disk: ~30-50 GB free for models (4B ~3 GB, 9B ~6 GB, 12B ~8 GB, plus downloads and a backup copy).
- Software: Ollama or llama.cpp server (GGUF), or `mlx_lm.server` (MLX). Both expose an OpenAI-compatible endpoint, so the web app only needs a base URL and model name from `.env`.
- Vision/OCR: Gemma-SEA-LION-v4-4B-VL can read menu photos directly (test Thai and Burmese accuracy; expect to correct items by hand on the review screen). Free fallbacks: Tesseract (has `tha` and `mya` language packs) and Apple Vision.

### 9.4 Scaled-down stack for the laptop
- Web app: Next.js + Tailwind, run locally.
- Database and auth: Supabase free project or local SQLite/Postgres (simplest for a class demo: SQLite via Prisma).
- Model: Ollama / mlx_lm.server on localhost:11434 or :8080.
- Demo on phones: same Wi-Fi via the laptop's local IP, or a free Cloudflare Tunnel / ngrok URL so the QR code works from any phone.
- No Vercel bill, no GPU rental, no API cost. If the model is too slow or wrong on demo day, keep a hosted-API fallback (env var swap) only as emergency backup.

### 9.5 University-scale scope
Keep (P0 only): 1.1 menu page, 1.2 chat, 1.3 allergen template, 1.4 Thai/Burmese/English, 1.8 fallback, 2.1 login, 2.2 photo import with review, 2.3 item editing, 2.5 sold-out toggle and hours, 2.6 FAQ + persona, 2.7 QR codes, 2.8 test panel, 3.1-3.3 grounded AI pipeline.
Stretch (if time): 2.9 question insights (this is your most original feature for the report).
Drop: billing, super-admin, LINE/WhatsApp, POS, payments, multi-location, AI dish images.

### 9.8 Friend's gaming laptop (optional, borrowed, not a dependency)
This laptop belongs to a friend, so the project must work fully on your MacBook Air M4 alone. Use the friend's laptop only for extra tests (e.g. a one-day benchmark of the 9B/12B models) or as a demo booster if they agree.
An NVIDIA gaming laptop is usually faster than the M4 Air for this: dedicated GPU memory (VRAM) with higher bandwidth (about 250-500 GB/s vs 120 GB/s) and much faster prompt reading. What matters is the GPU model and its VRAM (not system RAM). Estimates, 4-bit models in Ollama / llama.cpp / vLLM:

| Laptop GPU VRAM | Largest practical model | Est. speed |
|---|---|---|
| 6 GB (e.g. RTX 3050/4050) | 4B (Gemma-SEA-LION-v4-4B-VL) | 40-60 tok/s |
| 8 GB (RTX 3060/4060/4070 laptop) | 9B tight, 4B comfortable | 9B: 30-45 tok/s |

| 16 GB (RTX 4090/5080 laptop) | 12-14B comfortably; 27B is still too tight | 30-50 tok/s (14B) |

If your friend agrees, a possible split: run the model server on the gaming laptop (plugged in, cooling on) and develop the web app on the Air, calling the model at `http://<laptop-ip>:11434` over the same Wi-Fi (or Tailscale). Keep the Air as a fallback that can run the 4B alone, so the demo still works if the gaming laptop is unavailable. ### 9.9 Decision: MacBook Air M4, 32 GB
32 GB gives about 21-24 GB usable by the GPU by default (more if you raise the limit with `sudo sysctl iogpu.wired_limit_mb=...`, resets on reboot). Consequences:
- **Development/demo model (default): gemma4:12b (chosen by the Week 2 test, see section 10).** Original candidates were Gemma-SEA-LION-v3-9B-IT and gemma-3-12b. Both fit with room for the menu cache, browser and database. Est. 10-18 tok/s.
- **Fast option: Gemma-SEA-LION-v4-4B-VL** for menu-photo reading and as a low-latency fallback (30-40 tok/s).
- **27B (SEA-LION v4 27B GGUF/MLX 4-bit, ~15-16 GB):** loads, but at about 5-7 tok/s and with little memory left. Use it only as a reference in the model comparison ("how much better is the big model?"), not for the live demo.
- Run one model at a time; close heavy apps during tests. Budget: macOS 5 GB + apps 5 GB + model 6-8 GB + cache 2 GB = 18-20 GB, leaving headroom.
- Week 1 checklist: install Ollama (or `pip install mlx-lm`), pull the 4B-VL, 9B and 12B, record tokens/s, first-token time with/without cache, and memory in Activity Monitor.

## 10. Model comparison results (Week 2, run 2026-09-21 on the MacBook Air M4, 32 GB)

Setup: `eval/run_eval.py`, 30 questions (10 each in English, Thai, Burmese), sample menu of 13 dishes, Ollama, temperature 0.2. Raw answers: `eval/results/20260921-152810.json`; corrected scores: `eval/results/20260921-152810-rescored.json`.

| Model | Memory | Speed | Time/answer | Auto-check pass (after checker fixes) | Notes from reading the answers |
|---|---|---|---|---|---|
| **gemma4:12b** | 8.4 GB | 11 tok/s | 5.6 s | 100% (30/30) | Best in all three languages. Minor real error: for "vegetarian under 100 baht" (Burmese) it also listed Mango Sticky Rice at 100 and Fresh Spring Rolls, which have no vegetarian tag. Checker is lenient on this. |
| SEA-LION v3 9B | 6.9 GB | 15 tok/s | 11.5 s | 80% | Prompt-injection succeeded in Burmese (it said every dish costs 100 THB). Missed shellfish dishes in EN/TH/MY. Garbled Burmese in some answers. English answer with Thai/Burmese dish names was wrongly flagged. |
| qwen3:8b | 6.6 GB | 17 tok/s | 7.1 s | 77% (EN 100%, TH 90%, MY 40%) | Good English, weak Burmese. Said "no specified allergens" for a dish whose allergen data is missing (risky wording). |
| qwen3:4b-instruct | 3.9 GB | 30 tok/s | 3.6 s | 40% | Often answers Thai/Burmese in the wrong language. Not usable. |

Decision: **gemma4:12b is the default chat model.** Keep `qwen3:8b` as a fast English-only fallback; drop SEA-LION and the 4B.

Checker fixes made after reading failures (false alarms): dish names in any language now count; a price is checked against the dish beside it (window bug fixed); English answers may include Thai/Burmese dish names. Caveats: 10 questions per language is a small sample; automatic checks are keyword-based; no native Burmese speaker has reviewed the answers yet. One SEA-LION English answer is still flagged "wrong language" but is actually correct.

Consequences for the design:
1. Every model missed some shellfish dishes at least once, so allergen lists must come from the database (structured filter), never from model text (section 1.3).
2. A prompt-injection attempt worked on one model in Burmese, so keep the output checks (price and dish-name validation) and treat the system prompt as the second line of defence, not the first.
3. Prices and dish names in answers should be validated against the menu before showing them (same idea as `wrong_prices` in the eval script).
4. Next: have a native Burmese speaker rate the `gemma4:12b` answers, and repeat the run with 2-3 real restaurant menus and more questions.

### 10.1 Burmese review by a native speaker (2026-09-21)
The project owner (native Burmese speaker) reviewed gemma4:12b's Burmese answers over four rounds. Final round: 10/10 rated Good. Fixes that got there (all in `eval/run_eval.py` prompt, rules 7-9):
- Male polite spoken style ("ကျွန်တော်", sentences end "ပါတယ်ခင်ဗျာ"), never "သည်/ပါသည်", never "ရှင်/ကျွန်မ". Waiter gender becomes an owner setting in the dashboard (default male).
- Write "Allergens" in English; prices with "ဘတ်"; allergen names may stay English.
- Fixed staff line: "ဝန်ထမ်းကို မေးမြန်းပေးပါခင်ဗျာ"; missing dish: "ဆိုင်တွင် <name> မရောင်းပါဘူးခင်ဗျာ"; offer help: "ဘာကူညီပေးရမလဲခင်ဗျာ".
- Vegetarian requests list only dishes tagged vegetarian/vegan; allergy answers list only the asked allergen.
- Opening hours copied exactly from data (one round the model converted 22:00 to "8 pm": a real error, so hours come from the database).
In the app these become fixed templates from the database (allergen lines, hours, staff sentence, vegetarian filter), and the model only writes the short connecting sentences. Remaining risk: 10 Burmese questions and one reviewer; repeat with more questions and 2-3 real menus.

## 11. When the chat shows the menu (UI actions)

The AI ends every reply with a hidden line `ACTION: <json>`. The app removes that line, shows the text, and does what the action says. The customer never sees the line. Tests: `eval/run_actions.py` (gemma4:12b scored 17/18; the one miss was showing the menu after "Hello").

| Situation | Action | What the app shows |
|---|---|---|
| Customer asks to see the menu, what you have, wants to browse, or says "I want to order" without naming a dish | `show_menu` | Opens the full menu page inside the chat (category tabs, photos) |
| AI recommends or lists dishes (vegetarian, budget, "what's popular", allergen list) | `show_dishes` + up to 4 ids | Dish cards under the reply, tap for detail |
| Customer asks about one dish (price, ingredients, allergens) | `show_dishes` + that id | That dish's card with its allergen icons |
| Customer asks for a dish that is sold out | `show_dishes` + alternatives | Cards for alternatives (never the sold-out dish) |
| Customer says they want specific dishes ("I'll have the fried rice") | `add_to_picks` + ids | Adds to "My picks" list, shows it, with a "Show to waiter" / "Call staff" button (no payment in the first release) |
| Customer asks for the bill, to pay, to complain, or for a person | `call_staff` | Sends a call-staff notice for the table and confirms it |
| Greeting, hours, Wi-Fi, parking, dish not on the menu, refusal, small talk | `none` | Text only |

Rules the app enforces (never trust the model blindly):
1. Every id must exist in the restaurant's menu, otherwise the card is dropped. Sold-out dishes never appear as recommendations or in "picks".
2. Prices, allergens and photos on cards come from the database, not from the reply text.
3. If the ACTION line is missing or invalid, treat it as `none`, but a keyword fallback shows the menu for words like menu / เมนู / မီနူး.
4. A permanent "Menu" button stays on the chat screen, so the customer can always open the menu without asking.
5. The last action is logged with the question, so the owner insights (section 2.9) can show what people asked before ordering.
