# Shop AI's UI needs disclosure, not rebuilding

Shop AI's diner chat, menu, and staff/kitchen surfaces already embody the right *structural* choices — a picks-list instead of a cart, a floating three-button action bar, item-level allergen tags, template-first AI safety, a three-column kitchen kanban — but the actual code (Next.js 16.3.5, React 19.3.0, a hand-rolled ~120-line `globals.css`, no Tailwind) reveals that almost every concrete gap is a missing **disclosure**, not a missing feature: the AI waiter's Ollama call runs with `stream: false` and only a generic three-dot indicator, so a multi-second wait explains nothing about itself; `<html lang="en">` in `layout.tsx` never updates when a diner switches languages; the full-screen chat sheet has no dialog or live-region semantics for screen readers; the two whole-screen glass themes (`.aurora-d`/`.gd` and `.aurora-l`/`.gl`) carry no `prefers-reduced-transparency` fallback; and both staff dashboards poll every three seconds behind a bare LIVE/OFFLINE dot with no "as of HH:MM" timestamp. None of these require an architecture change — they are attributes, a media query, a timestamp, and a template tweak. The one place the app *does* deviate from established commercial patterns is the Waiter view's sold-out toggle, which sits behind a modal where Toast, Square, and Checkmate all use a single inline switch on the item row. Read together, the five research areas argue for a focused polish pass — streaming plus better fallback copy in chat, accessibility attributes, a contrast/motion audit under glass, dietary-wording and layout tightening on the menu, and a freshness indicator plus an inline sold-out toggle on staff screens — rather than a redesign or a framework migration.

## Chat feels slow because nothing streams, and dots don't explain why

Shop AI's AI waiter pipeline, traced through `app/src/app/api/public/[slug]/chat/route.ts` into `modules/ai/api/chat.ts` and `modules/ai/ai.ts`, only calls the language model for the "everything else" branch after seven rule-based intents (allergens, bill, vegetarian lists, named-dish pricing, pork, hours, menu display) are checked and answered from the database with fixed sentences; the model call itself, in `askModel()`, posts to Ollama with `stream: false`, caps `num_predict` at 220 tokens, and keeps only the last two turns of history — exactly the "smaller prompt, shorter history, capped reply length" optimization visible in the project's own recent commit history. While the model is generating, `Diner.tsx`'s `Chat` component shows nothing but a generic three-bubble `.dots` animation. This is precisely the pattern latency research treats as the weaker of two available techniques: token-by-token streaming is described as the single most effective approach to perceived latency because it converts a "waiting" experience into a "reading" one, with the first word appearing in 200–600ms even though total generation time is unchanged ([TianPan.co](https://tianpan.co/blog/2026/04/20/latency-perception-gap-ai-interfaces)), and a peer-reviewed study found long responses with no indicator scored 4.40 on satisfaction versus 5.67 for instant responses, with a typing indicator only partially closing that gap ([arXiv](https://arxiv.org/pdf/2507.22352)). A three-dot indicator is explicitly characterized as "slightly better than nothing" and "nowhere near the engagement level of true streaming" because it tells the user the system is working but not what it's doing or how far along it is ([Nowah](https://nowah.xyz/blog/streaming-ux-real-time-ai-responses)). Because Ollama's chat API natively supports `stream: true`, and Shop AI already separates instant, whole-template replies (allergens, prices, hours) from the one branch that actually has multi-second latency, the lowest-risk fix is a hybrid: stream only the free-form model branch, leave every templated safety reply exactly as instant and whole as it is today, and replace the generic dots with a state-labeled indicator (e.g., "Thinking about the menu…") so the wait at least discloses what is happening — a distinction the time-to-first-token/time-per-output-token framing makes directly, since a short TTFT with a longer total can still "feel responsive" ([DEV Community](https://dev.to/gabrielanhaia/ttft-vs-total-latency-instrumenting-what-users-actually-feel-5h0f)).

Two smaller chat-composer gaps compound the same "disclosure" theme. First, `Diner.tsx` only renders its three suggestion chips (`chips1/2/3`) when `msgs.length === 1`, i.e. strictly on the first turn — a legitimate pattern NN/g calls "conversation starters," but the same source documents a second, distinct pattern used by Perplexity and Gemini: follow-up suggestions regenerated *after every reply*, specifically to save users from retyping on a phone ([NN/g](https://www.nngroup.com/articles/prompt-controls-genai/)). Adding two or three dynamically generated follow-up chips after each assistant turn (e.g., "See vegetarian options," "Any drink pairing?") is the single most concretely actionable addition identified for the chat composer. Second, the `rate()` function in `Diner.tsx` sends only a bare `+1`/`-1` value to `/api/public/[slug]/feedback` with no follow-up — matching only the first of three layers a tiered feedback architecture recommends: zero-friction thumbs on every message, then a short categorized reason picker on thumbs-down ("Wrong info," "Didn't understand," "Missed allergen concern"), then an optional free-text field for the minority willing to elaborate ([The Training Boss](https://thetrainingboss.com/thumbs-up-down-for-llm-responses/)). Because Shop AI is an anonymous, no-account QR session, the free-text layer is the lowest-value tier to add; the categorized-reason layer on thumbs-down is the highest-value, lowest-effort one. Finally, the app's own `STAFF()` template in `ai.ts` already appends "Please confirm with the staff" to every allergen reply, and a persistent "Call staff" bell is always visible in the floating bar — a structural match to fallback-design guidance that condemns dead-end apologies and recommends a "visible lifeboat," a persistent human-escalation affordance that never has to be hunted for ([Asks.app](https://asks.app/blog/ai-human-handoff); [Beefed.ai](https://beefed.ai/en/chatbot-fallback-escalation)). What is missing is the connective tissue: the allergen-safety literature specifically warns against ever implying a dish is guaranteed safe and frames disclaimers as trust-building rather than trust-eroding ([menumiz](https://brand.menumiz.com/2026/01/31/why-most-ai-restaurant-bots-fail-and-what-actually-works/); [Hostie.ai](https://hostie.ai/resources/voice-ai-allergy-dietary-questions-menu-aware-bots-2025)), and Shop AI's `UNSAFE` regex in `checkModelReply()` already blocks phrases like "allergy-free" or "guaranteed" from the model — a well-built guardrail that the report validates rather than flags as a gap. The one addition worth making is a repeated-fallback counter: after two consecutive `answered:false` results in one conversation, the UI should proactively surface the "Call staff" action inline rather than waiting for the diner to notice the separate bell, which matches the escalation-trigger guidance of counting fallbacks rather than relying purely on user-initiated requests ([Beefed.ai](https://beefed.ai/en/chatbot-fallback-escalation)).

## Three accessibility gaps sit directly in the code, not in judgment calls

Reading `app/src/app/layout.tsx` alongside `Diner.tsx` surfaces a clean, unambiguous WCAG gap: the root layout hardcodes `<html lang="en">`, and `Diner.tsx`'s `chooseLang()` function updates only React state and `localStorage` — `document.documentElement.lang` is never touched. WCAG's Success Criterion 3.1.1 requires that a page's default language be programmatically determinable via that attribute ([W3C](https://www.w3.org/WAI/WCAG22/Understanding/language-of-page.html)), and the standard single-page-app remedy is to update `document.documentElement.lang` in a layout effect the moment the locale changes ([TOPdesk](https://techblog.topdesk.com/accessibility/language-and-accessibility-on-the-internet/)) — a change lands in time for most assistive technology, given the roughly 100ms gap typically observed between a DOM update and a screen reader announcing it ([Craig Abbott](https://www.craigabbott.co.uk/blog/2022/using-the-language-attribute-to-make-your-website-accessible/)). This is a one-line fix keyed to the existing `lang` state, not a redesign.

The second gap sits in the `Chat` component's markup: the chat sheet is a plain `<div className="chat-sheet aurora-d">` with no `role="dialog"`, no `aria-modal="true"`, and no focus management on open or close, while its message list is a plain scrollable `<div>` with no `role="log"` or `aria-live` attribute at all. Standard modal-dialog practice requires focus to move into the dialog on open, stay trapped inside it, and return to the trigger element on close ([W3C WAI-ARIA APG](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/); [Deque](https://www.deque.com/blog/aria-modal-alert-dialogs-a11y-support-series-part-2/)), and `aria-modal="true"` is specifically what tells assistive technology the rest of the page is inert until the dialog closes ([MDN](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-modal)). Separately, chat transcripts are the canonical example of a `role="log"` region with `aria-live="polite"` and no `aria-atomic`, so only the newly appended message — not the whole history — is announced each time ([Ionic](https://ionic.io/docs/accessibility/aria-live)); this pattern is also the direct implementation path for WCAG 4.1.3 (Status Messages), which explicitly names a "someone is typing" state as an example status message that must be programmatically determinable ([WCAG.com](https://www.wcag.com/developers/4-1-3-status-messages/); [W3C](https://www.w3.org/WAI/WCAG21/Understanding/status-messages.html)) — meaning the same `.dots` loading state discussed above needs an ARIA status role regardless of whether streaming ships, since a purely visual animation announces nothing to a screen-reader user. Both fixes are scoped to the `Chat` component's JSX: add `role="dialog"`/`aria-modal`/focus handling to the sheet container, and wrap the message list in `role="log" aria-live="polite"`.

The third gap is typographic and asymmetric: `Diner.tsx` sets `lineHeight: lang === "my" ? 1.9 : 1.5` on chat bubbles, bumping only Burmese. Both Burmese and Thai script stack diacritics, vowel signs, and tone marks above and below the base consonant, which is why both need substantially taller line-height than Latin text to prevent overlap between lines — this is documented for Thai specifically, with fallback fonts required to *share* rather than shrink the root font's line-height ([Wikipedia, Thai typography](https://en.wikipedia.org/wiki/Thai_typography); [W3C](https://www.w3.org/International/articles/typography/fontstyles.en.html)), and separately for Burmese, where the same overlap failure mode is described as a recurring, well-documented rendering bug ([1StopAsia](https://www.1stopasia.com/blog/burmese-production-guardrails-script-rendering/); [GitHub](https://github.com/openmaptiles/fonts/issues/14)). Shop AI's 1.9-for-Burmese choice is directionally sound but currently leaves Thai bubbles under-spaced for no principled reason; the fix is an empirically-tuned Thai-specific value, not necessarily 1.9. The same file's `priceLabel()` function, by contrast, is already correctly differentiated: it renders Burmese digits for `my` and Arabic digits for `th`/`en`, which matches the documented convention split almost exactly — Thai commercial writing has largely moved to Arabic numerals while Myanmar retains far stronger everyday use of native digits ([SEAtongue](https://seatongue.com/resources/language-center/thai-localization-guide/); [Fifty Viss](https://viss.wordpress.com/2015/06/07/will-burmese-numerals-ever-fall-out-of-fashion/)) — this is a place the code already got a subtle multilingual detail right and should be left alone. One further, sharper gap than the research notes anticipated: `OwnerShell.tsx` and every `owner/*` page hardcode English strings directly in JSX with no dictionary or `tr()`-style function at all, unlike the diner module's `i18n.ts`. Standard i18n practice treats engineering infrastructure (externalized strings, a lookup mechanism) as a one-time investment built everywhere up front, with the *translation* of admin/back-office screens reasonably deferred behind customer-facing surfaces ([SimpleLocalize](https://simplelocalize.io/blog/posts/i18n-for-saas-teams/); [SimpleLocalize](https://simplelocalize.io/blog/posts/internationalization-guide-software-localization/)) — but no source frames a permanently English-only admin surface as acceptable, only as deferred scope, so the near-term fix is building the dictionary *mechanism* for the owner shell now (mirroring `i18n.ts`) even while Thai/Burmese owner-facing translation itself stays on the backlog. Finally, the gendered-particle system in `ai.ts` — the `particle()` function keyed to `restaurant.persona.gender`, a single fixed brand-level setting rather than anything inferred per diner — is worth calling out as a validated good pattern, not a gap: localization guidance frames choosing a gendered voice as a deliberate, one-time brand decision precisely because it "assigns a perceived gender identity to your brand voice" ([Thiantawan](https://medium.com/@thiantawan/ux-writing-challenges-inclusive-pronouns-in-thai-localization-3cb659563277)), while broader chatbot-design literature warns specifically against *inferring* a customer's own gender from limited signals ([Atomic Object](https://spin.atomicobject.com/2020/10/27/gender-bias-ux-design)) — Shop AI's architecture already avoids that exact pitfall by never touching the diner's gender at all.

## Whole-screen glass sits at the overused end of a 2025-2026 design trend

`globals.css` applies `.aurora-d`/`.gd` (dark glass, `backdrop-filter: blur(18px) saturate(150%)`) as a full-viewport background on the diner and staff surfaces, and `.aurora-l`/`.gl` (light glass, `blur(22px) saturate(140%)`) the same way on owner and auth screens — persistent, large-area glass rather than a small accent, on phone-class devices for three of the app's four surfaces. This is squarely the pattern current guidance warns about: glassmorphism has a structural accessibility problem because a translucent panel's contrast ratio is a property of whatever happens to sit behind it, not of the component itself, making WCAG 2.2's 4.5:1 (normal text) and 3:1 (large text) minimums impossible to guarantee in advance ([W3C](https://www.w3.org/WAI/WCAG21/Understanding/contrast-minimum.html)); one measured example showed the *same* translucent component scoring 5.2:1 over a dark background and only 1.8:1 over a light one ([Codexical](https://www.codexical.com/posts/2026-04-24-glassmorphism-accessibility)). Shop AI's case is actually easier to audit than the general problem, precisely because the background is fixed and known rather than user-supplied: the "test over five wallpapers" methodology sources recommend doesn't apply, but the underlying fix set does — a per-class contrast check of `.chip`, `.pill`, `.soft-d`, and `.soft-l` text against the exact, static `.gd`/`.gl` background colors is a one-time, deterministic audit rather than an ongoing testing burden. The recommended mitigations are concrete and additive: maintain a semi-opaque fill behind body text rather than compromising it for the aesthetic, add a border to reinforce which regions are interactive, and — critically for a project with no such handling today — respect `prefers-reduced-transparency` by building a solid baseline and layering transparency on top only inside a `no-preference` media query ([Axess Lab](https://axesslab.com/glassmorphism-meets-accessibility-can-frosted-glass-be-inclusive/); [Chrome for Developers](https://developer.chrome.com/blog/css-prefers-reduced-transparency)). Performance is the second half of the same coin: `backdrop-filter` is GPU-accelerated but web.dev's own guidance is blunt that it "may harm performance — test it before deploying" ([web.dev](https://web.dev/articles/backdrop-filter)), and mobile devices typically handle three to five simultaneous blur effects well before jank sets in — a budget Shop AI should check explicitly wherever a blurred `.modal-back` (currently `blur(4px)`) sits on top of an already-blurred `.aurora-d`/`.aurora-l` background, since diner, waiter, and chef are all phone- or tablet-class devices, exactly the hardware class the performance warning targets. None of this argues for abandoning the aesthetic — glass is explicitly framed as "a spice, not a meal," appropriate for modals, notification overlays, and dashboards in moderation ([Pravin Kumar](https://www.pravinkumar.co/blog/should-you-use-glassmorphism-website-2026)) — but it does argue for treating the whole-screen application as the more overused end of that spectrum and adding the contrast/opacity/media-query safety net current implementations mostly skip.

The CSS architecture underneath the glass is a natural place to make that fix durable. Shop AI's `globals.css` is already a well-scoped utility-class vocabulary (`.btn`, `.chip`, `.pill`, `.in`, `.switch`, `.meter`, `.modal`, `.toast`, `.kanban`, `.alert-banner`) at roughly 120 lines with no Tailwind, no CSS Modules, and heavy inline `style={{}}` usage in every component read — exactly the "shared atoms" tier small-team design-system guidance says to prioritize, and exactly the scale at which that guidance says a full framework migration is disproportionate risk: "Tailwind trades HTML readability for CSS consistency, while vanilla CSS trades setup speed for long-term flexibility — neither tradeoff is universally right" ([Measured](https://measured.co/blog/tailwind-trade-offs)), and teams this size are explicitly told that "teams that start with component libraries fail; teams that start with tokens survive" ([Fordel Studios](https://www.fordelstudios.com/research/design-systems-from-scratch-small-teams)). The lower-risk path is formalizing the existing `:root` custom properties into a documented raw scale plus semantic roles — a spacing scale, a handful of named color roles that resolve differently under the dark-glass and light-glass surfaces (e.g., a `--text-on-glass` role rather than the ad hoc `.soft-d`/`.soft-l` split already present) — which costs no build tooling and directly doubles as the token layer the contrast audit above needs anyway ([UXPin](https://www.uxpin.com/studio/blog/managing-global-styles-in-react-with-design-tokens/)). If the team later wants a genuine user-togglable brightness preference layered on top of (not replacing) the current per-surface dark/light role split, the standard mechanism transfers directly: store the choice in a cookie or `localStorage`, apply it via a `data-theme` attribute set before hydration, and let `next-themes` distinguish the user's stated preference from the resolved value ([GitHub, next-themes](https://github.com/pacocoursey/next-themes); [dev.to](https://dev.to/137foundry/how-to-prevent-the-flash-of-wrong-theme-when-implementing-dark-mode-2pg1)) — but this is future-facing infrastructure, not a near-term priority next to the contrast and transparency fixes above.

## Menu and ordering UX already matches best practice; wording and density need tightening

`Diner.tsx`'s core ordering pattern validates cleanly against the research: the fixed bottom bar with "Ask the waiter," "Call staff," and a conditional "My picks" summary is a textbook floating-action-button implementation — fixed position, always reachable through scrolling, not buried behind a menu tap, which is precisely what chatbot-entry-point guidance recommends because "users instinctively look for chat widgets there" ([Widget Chat](https://widget-chat.com/blog/chatbot-ui-design-best-practices/); [Eyaana](https://eyaana.com/blogs/uiux-design-optimizations-make-the-chatbot-noticeable-and-inviting/)). The "picks" list itself — a simple stepper, no checkout language, framed as "Show to waiter" rather than "Submit order" — maps almost exactly onto the wishlist-versus-cart distinction in the literature: a cart signals immediate transactional urgency while a wishlist signals calmer, curatorial browsing intent, and different UX treatments follow from that difference ([NN/g](https://www.nngroup.com/articles/wishlist-or-cart/)). And the `AllergenChips` component's item-level tags on every `DishCard`, rather than a single page-bottom disclaimer, is the legally and practically correct pattern: allergen disclosure guidance is explicit that it "is not a general disclaimer at the bottom of the page — it is item-level disclosure" ([ADDE Act guide](https://adde.food-regulations.org/how-to-list-allergens-on-a-menu/)), and point-of-order phrasing precedents from jurisdictions that regulate this directly reinforce pairing every tag with staff-confirmation language rather than relying on the tag alone ([Natick, MA](https://natickma.gov/DocumentCenter/View/5491/Certifications-Signage-and-Menu-Wording)).

Three smaller, concrete fixes remain. First, the dietary pills in `i18n.ts` (`vegetarian`, `noPeanuts`) should standardize on unambiguous "-free" suffix wording site-wide — Grubhub's dietary-filter research found that "free"-suffixed phrasing (e.g., "Milk-free") measurably resolves user confusion over whether a filter includes or excludes an ingredient, compared to vaguer single-word tags ([Silvia Diff](https://www.silviadiff.com/grubhub-dietary-filters)), and "No peanuts" already gets this right while other pills could follow the same convention consistently. Second, the sold-out treatment in `DishCard` — dimming to reduced opacity while keeping a "Sold out today" chip and the card itself tappable — already matches the recommended pattern of making unavailability obvious without hiding the item entirely, consistent with guidance that stale availability is "one of the most trust-eroding moments" for a digital menu and that disabling rather than letting a user hit a post-hoc error is the safer default ([Dineazi](https://dineazi.com/resources/qr-menu-design-tips); [UX Beginner](https://uxbeginner.com/ecommerce-ux-design-sell-out/)) — this is a validation, not a fix. Third, and more actionable: at a 390px viewport, `Diner.tsx` stacks a search bar, a category-pill row, and a dietary-pill row before the dish list even starts, which risks pushing content below the fold on the phone-class device every diner uses. Mobile filter-placement research treats sticky, always-reachable category access as the priority and recommends collapsing secondary filters behind an expandable control rather than permanently consuming vertical space ([SetProduct](https://www.setproduct.com/blog/filter-ui-design)), while menu-design guidance separately recommends keeping category navigation "above the fold" within a tight 5–8 category range and named the way guests actually talk ([NN/g](https://www.nngroup.com/articles/menu-design/)) — the concrete fix is making the category-pill row sticky while collapsing the dietary-pill row behind a small "Filters" toggle. It is worth being direct about a genuine limitation of this research area: no named commercial product (DoorDash, Uber Eats, GoDine, Feedify) was found to document a "browse and flag for staff, no payment" experience matching Shop AI's actual model, so the picks-list pattern is a defensible adaptation of adjacent wishlist and physical table-flagging precedent rather than a directly proven case study — a genuine gap worth flagging rather than papering over.

## Staff and kitchen dashboards match KDS convention but skip two cheap wins

`ChefPage.tsx`'s three-column kanban (New → Cooking → Ready) is already the minimal, standard food-service Kanban layout — "Incoming Orders," "Preparation/Cooking," and "Ready" are the columns named directly in food-service Kanban templates, with the stated purpose of making work-in-progress visible to prevent bottlenecks ([ClickUp](https://clickup.com/templates/kanban-board/food-service-industry); [Growing Scrum Masters](https://www.growingscrummasters.com/keywords/kitchen-kanban/)) — so a fourth "Plating"/"Expo" column some vendors use should be added only if the restaurant's actual workflow needs it, not as a default best-practice mandate. The allergy banner rendered on both `ChefPage.tsx` and `WaiterPage.tsx` (`.alert-banner`: solid red background, a warning icon, and literal "ALLERGY" text) already implements the core safety-redundancy pattern the research converges on: never encode a safety alert as color alone, since roughly 8% of male users have some form of color vision deficiency and cannot reliably distinguish red alert states from surrounding UI without a paired icon and label ([kwickos](https://kwickos.com/blog/allergen-management-restaurant-guide.html); [DEV Community](https://dev.to/alphashark/8-of-your-male-users-cant-see-your-red-error-states-design-for-color-blindness-2ofa)) — this is a component the app already got right and should preserve exactly as built. One refinement is available, though: today only the elapsed-time *text* on a chef ticket shifts to pale red once a ticket passes ten minutes, while the ticket card itself stays visually identical regardless of urgency. Commercial KDS products implement a full traffic-light treatment — green/on-time, yellow/caution, red/late — with configurable thresholds so staff read status "all through color-coded visual alerts" without doing timestamp math ([Fresh KDS](https://www.fresh.technology/kds-features/on-time-caution-late-ticket-headers)); extending Shop AI's existing threshold logic from the timer text to the ticket card's border or background would close that gap cheaply, using color the app already computes.

Two gaps are worth fixing directly. First, both `ChefPage.tsx` and `WaiterPage.tsx` poll `/api/staff/kitchen` and `/api/staff/floor` every three seconds via `usePoll` and show only a LIVE/OFFLINE status dot — no "as of HH:MM" timestamp, no explicit reconnecting state. Operational-dashboard research is emphatic that the polling interval itself is usually fine (three seconds sits comfortably inside the range practitioners call "responsive enough to feel real-time," and users only perceive delay above roughly 200–300ms for genuinely live interactions) but that the *disclosure* of freshness matters more than the raw interval: the recommended pattern is an explicit "Data as of…" label or a "Live/Stale/Paused" status, with auto-retry and a visible "Offline… Reconnecting…" banner on failure ([Smashing Magazine](https://www.smashingmagazine.com/2025/09/ux-strategies-real-time-dashboards/); [DEV Community](https://dev.to/heyshreee/building-a-real-time-dashboard-1gf1)) — Shop AI's binary dot is a good start but stops short of that disclosure. Second, `WaiterPage.tsx`'s sold-out toggle lives behind a `dishOpen` modal reached via a "Mark a dish" button, while the three commercial POS/KDS products examined (Toast, Square, Checkmate) all implement the equivalent "86" action as a single switch directly on the item, with no intermediate screen ([Toast](https://support.toasttab.com/en/article/86-an-Item); [Square](https://squareup.com/help/us/en/article/8430-mark-items-and-modifiers-as-sold-out); [Checkmate](https://support.itsacheckmate.com/hc/en-us/articles/8136678055963-Mark-Items-Modifiers-as-Sold-Out-86-d)). This matters specifically because touch-pointing accuracy measurably degrades as walking speed increases, which is the normal state for waitstaff on a floor ([arXiv](https://arxiv.org/pdf/2101.05244)), and critical, frequent actions are recommended to sit in the thumb-reachable bottom third of the screen with the fewest possible taps rather than behind a navigation step ([UXPin](https://www.uxpin.com/studio/blog/responsive-design-touch-devices-key-considerations/)) — collapsing the modal into an inline switch on each dish row in the existing "Sold out now" summary bar is a direct, low-effort alignment with that convention. Both fixes are worth prioritizing over any new feature: the clearest documented failure mode across commercial POS/KDS products is not a missing capability but friction compounding at scale — one industry estimate puts a 15-second-per-transaction delay across 300 daily transactions at over 450 lost staff-hours a year, with non-intuitive interfaces cited as a contributor to the restaurant industry's roughly 75% annual staff turnover ([Xenia](https://www.xenia.team/articles/pos-system-training); [TapTouch POS](https://taptouchpos.com/blogs/common-pos-system-problems-in-restaurants/)) — a strong argument for protecting Shop AI's current interaction simplicity rather than layering more onto it.

## Conclusion

The through-line across all five areas is that Shop AI's hardest design decisions — how to represent an order without a cart, how to keep an LLM from inventing an allergen claim, how to lay out a kitchen queue, how to gender a virtual waiter's speech — were already made correctly, and made correctly without much external validation available to lean on, since named case studies for QR-menu-plus-AI-assistant products and Myanmar/Thai-script UI conventions remain thin in the published literature. What the code review surfaces instead is a consistent pattern of unfinished *disclosure*: state changes that happen in the backend or in React state but never reach the DOM attribute, the ARIA tree, or the pixel a diner or staff member is actually looking at. That reframes the roadmap usefully — the next sprint's highest-leverage work is not a design-system migration, a payment flow, or a rewrite of the AI pipeline, but a short, mechanical punch list: sync `lang` on language change, add dialog and live-region roles to the chat sheet, stream the model branch while keeping templates instant, bump Thai line-height, add a reduced-transparency media query, extend the ticket-urgency color from text to card, add a freshness timestamp, and move the sold-out toggle inline. Each is small enough to ship independently and verify in isolation, which — given the project's admitted lack of any prior device-class QA — also argues for treating "run the app once on a real 390px phone and a real kitchen-mounted display and screenshot the result" as the actual first step before any of the above, since several of these fixes (contrast under glass, backdrop-filter cost, Thai line-height) cannot be judged correct from source code alone.
